**证据 D（最关键）：仿真不可能报出 LUT 和 slice 占用。**

- **仿真（Simulation）**：给电路喂输入波形，看输出对不对。它算的是"逻辑功能对不对"，**不知道也不关心"用掉多少个 LUT"**。
- **综合（Synthesis）**：把 Verilog 代码翻译成 FPGA 里的 LUT、寄存器、RAM、DSP 等**实体资源**。**只有到这一步才会出现 LUT/slice 数字。**
- **布局布线（Place & Route）**：把这些资源真正摆到芯片的具体位置上、连好线，并计算延迟。这一步给出**最终**的占用和时序。

所以：**你能报出 LUT 和 slice 数，就说明你干的是综合/布局布线，不是仿真。** 这两件事在 FPGA 流程里是完全不同的环节。

| 违例终点数（S-EP / H-EP） | 0 / 0 | ——（.ts 不含此项） |

**怎么读这四个数（通俗版）：**

- **WNS（Worst Negative Slack，最差裕量）**：所有时序路径里**最紧的那一条**还剩多少富余时间。
  - **正数 = 有余量 = 通过**；**负数 = 时间不够 = 违例**。
  - 你的是 +1.408 ns，意思是"最紧的那条路，还多出 1.408 纳秒的余量"。**通过。**
- **TNS（Total Negative Slack，总违例量）**：所有违例路径的"欠账"加起来。
  - 你的是 **0**，意思是**一条违例都没有**。这是比 WNS 更彻底的"干净"。
- **SWNS/HWNS 里的 S/H**：S = Setup（建立），H = Hold（保持）。这是两种最基本的时序检查，后面名词表会讲。
- **"布局布线后 WNS(1.408) 比综合后 WNS(0.860) 更好"**——这是正常且常见的好现象。综合时用的是"估计的线延迟"，布线完了拿到**真实线长**，工具重新优化了一轮，所以变好了。

### 2.4 为什么 `49.60%` 和 `15.98%` 差 3.1 倍？（这是本轮最值得你学会的一件事）

两个数都**没错**，它们算的是**不同的东西**。

**`gate.area` 的 49.60% 从哪来**（看该文件第 20–28 行）：

```
Utilization Statistics
#slice*                 10524   out of  21216   49.60%
  #used ram               408
    #dram lut             296
    #shifter lut          112
  #used logic           10116
    #with luts*          5859
    #with adder          2974
    #reg only*           1283
```

- `#slice* = 10524 = #used ram 408 + #used logic 10116`
- 而 `#used logic 10116 = 5859（带 LUT 的）+ 2974（带加法器的）+ 1283（纯寄存器）`
- 这是**"如果每个 LUT、每个加法器、每个寄存器各占一个 slice"的未打包上界**。

**`gate.qor` 的 15.98% 从哪来**（看 `gate.qor` 第 17–23 行）：

```
|     #slices               |         3391                |
|     slices percentage     |       15.98%                |
|     #RAMs                 |           40                |
|     #DSPs                 |            8                |
|     #MACROs               |          207                |
|     #insts in MACRO       |         3458                |
```

- 关键是 `#MACROs 207` + `#insts in MACRO 3458`：工具把 **3458 个小单元打包进了 207 个 MACRO**（宏单元，一坨紧密相关、可以共用资源的逻辑）。
- **打包之后**，实际需要占用的物理 slice 就降到了 **3391**。

**通俗类比：**
- `.area` 的 49.60% ≈ "10 个人要坐，每人占一个座位，如果一人一座需要 10 个座位"（**上限**）
- `.qor` 的 15.98% ≈ "工具让其中 7 个人挤进了双人座，实际只占了 3.4 个座位"（**打包后估计**）
- 真实值在**布局布线之后**才能定下来，因为只有那时候才知道"到底挤不挤得下、会不会因为布线被迫拆开"。

**而且 `gate.area` 自己就在第 46 行承认了这一点**（原文）：


翻译：**"优化-门级之后的 LUT 和 Slice 数量不是最终值，请运行优化-布局以获得更接近实际的数量。"**

### 2.5 顺便说一个"口径陷阱"，你有真实数字可以拿来练手

你的器件对外的两个口号数是（来自选型表）：

- **LUT4 = 38,189**
- **slice = 21,216**

它们的换算是：**LUT6 × 1.8 ≈ LUT4**，即 21,216 × 1.8 = 38,188.8 ≈ **38,189** ✅（自洽）。也就是说，**"slice 21,216"和"LUT4 38,189"其实是同一批硬件的两种数法**。

**那么下面这个算法是错的：**

```
12705 / 38189 = 33.27%   ← ❌ 错！
```

因为分子 `#lut 12705` 是 **LUT1+LUT2+LUT3+LUT4+LUT5+LUT6 混在一起**的个数（你看 `gate.area` 第 10–15 行，六种都列了），分母 38,189 是**纯 LUT4 口径**。**分子分母口径不一致，除出来的百分比没有意义。**

**正确做法：只用"slice 对 slice"这一条口径。**

```
10524 / 21216 = 49.60%   ← 综合后未打包上界（口径自洽，但不是最终值）—— 数值上界
 3391 / 21216 = 15.98%   ← 综合后打包估计（口径自洽，但不是最终值）—— 数值下界
12358 / 21216 = 58.25%   ← ✅【已实测·最终值】布局布线后（这才是能写进答辩的那个数）
```

**答辩材料里，占用率只写一条：`12358 / 21216 = 58.25%`。** 对外提资源规模时，用 LUT4 = 38,189 和 DFF = 42,432 描述这颗芯片有多大即可。

（15.98% 和 49.60% 现在可以彻底放下了：前者乐观了 3.6 倍，后者乐观了 8.65 个百分点。它们只是综合阶段的"过程值"。）

**名词解释（先看这里，再去看报告）**
- **LUT（Look-Up Table，查找表）**：FPGA 实现"组合逻辑"的基本单元。你可以把它想成一张**真值表**：给它几个输入，它按事先存好的表吐出对应输出。比如实现"两输入与门"，就是在表里存 `00→0, 01→0, 10→0, 11→1`。**输入端的个数叫"LUT 几"**：LUT4 = 4 输入查找表，LUT6 = 6 输入查找表。输入越多，一个 LUT 能顶的逻辑越复杂。
- **Slice**：芯片里**一个物理格子**，里面装若干 LUT + 若干寄存器 + 进位/加法链等。**"占用率"通常就是指 slice 占用率**，因为 slice 是真实存在的物理资源。你芯片有 21,216 个 slice。
- **DFF（D Flip-Flop，D 触发器）/ 寄存器（Register）**：存 1 bit 的"存储格子"，靠时钟边沿更新。**LUT 管"算"，DFF 管"记"。** 你的芯片有 42,432 个 DFF。设计里寄存器多了会同时吃 DFF 和 slice。

- **分布式 RAM（DRAM / dram lut）**：用**LUT 硬凑出来的小内存**，容量小但灵活。报告里 `#dram lut 296`。
- **DSP**：专门做**乘法/累加**的硬件单元。用 DSP 做乘法比用 LUT 拼又快又省。你的芯片有 40 个，现在用了 8 个（20%）。
- **PLL（Phase-Locked Loop，锁相环）**：把输入的晶振频率"倍频/分频"成你要的各种时钟。你用了 3 个，芯片共 6 个。
- **扇出（Fanout）**：一个信号要驱动多少个下游输入。**扇出越大，这个信号越难布线和满足时序**，所以工具会用"全局时钟网络"来分发时钟。

### 🔴 P0-2：时序四件套（SWNS / STNS / HWNS / HTNS）与"时序"到底是什么

**学什么**

**为什么学**
- 时序是 FPGA 的**核心概念**，答辩必问，而且是**唯一你现在就能对外说的硬结论**。会读它，你的"我跑通了"才有分量。
- 硬件到货后如果画面出问题（花屏、撕裂、闪烁），**第一个要排查的就是时序**，而不是先怀疑代码。

**用哪个文件学**
- `best_result\camera_to_dsi_display_phy.ts`（4 个数）
- `syn_1\gate.qor`（第 4–10 行 `Timing` 段）
- `syn_1\camera_to_dsi_display_gate.timing`（共 29,792 行，**别全看**，只看第 25–30 行的 `Timing Status`、第 32–67 行的 `Clock Summary`）

**学到什么程度算完成**
1. 我能背出"WNS 是正数就通过"这句话，并说清 WNS 和 TNS 的区别。
2. 我能解释"建立时间 = 数据要在时钟边沿之前多久就稳定下来"。
3. 我能解释"保持时间 = 数据在时钟边沿之后还要保持多久不变"。
4. 我能说出我的设计最紧的那条路在 `HDMI_SERIAL_CLK`（375 MHz）上。
5. 我能解释为什么"布局布线后的余量(1.408 ns)比综合后(0.860 ns)更大"。

**名词解释**
- **时序（Timing）**：信号从一个寄存器出发、经过一堆 LUT、到达下一个寄存器所需要的**时间**，和时钟给出的**时间预算**之间的比较。通俗说：**"这活儿在一个时钟节拍内干得完吗？"**
- **时钟周期 / 频率**：周期是"一个节拍多长"（单位 ns），频率是"一秒多少个节拍"（单位 MHz）。**周期 × 频率 = 1**。例：`HDMI_PIXEL_CLK` 周期 13.333 ns ↔ 75 MHz（13.333 ns × 75 MHz ≈ 1）。
- **建立时间违例（Setup Violation）**：数据**来得太晚**，没能在时钟边沿之前稳定下来。**组合逻辑太长会导致它。** 表现为 WNS 为负。
- **保持时间违例（Hold Violation）**：数据**变得太早**，把上一个节拍该被采的值冲掉了。**通常由布线延迟太短引起**，和逻辑长短关系不大。
- **Slack（余量）**：`预算时间 − 实际需要时间`。**正数=通过，负数=违例。**
- **WNS（Worst Negative Slack）**：所有路径里**最差的那一条**的余量。虽然名字里有 "Negative"，但它**正负都可能**，正数就代表全部通过。
- **TNS（Total Negative Slack）**：把所有**违例路径**的负余量加起来。**TNS = 0 表示一条违例都没有**，这是最强的"干净"证据。
- **时序收敛（Timing Closure）**：所有路径的余量都 ≥ 0，即没有违例。
- **关键路径（Critical Path）**：余量最小（最紧）的那条路径。
- **STA（Static Timing Analysis，静态时序分析）**：**不跑仿真、不喂波形**，直接按所有路径的延迟算余量。所以它能检查全芯片所有路径。（注意：这又一次说明时序分析不是仿真。）你报告里的 `STA coverage : 94.53%` 就是它覆盖了多少路径。
- **逻辑级数（Logic Level）**：一条路径上串了多少级 LUT。级数越多，延迟越大。你 `gate.qor` 第 48–67 行有一张 `Logic Level Distribution` 表，能看到各时钟下各级数各有多少条路径。

|---|---|---|
| 1 | `create_clock` | **定义第一个真实时钟**：外部晶振从引脚 `I_sys_clk` 进来，周期 20 ns（= 50 MHz），波形是 0 ns 上升、10 ns 下降（即 50% 占空比）。这是**唯一的外部时钟源**。 |

|---|---|---|

**名词解释**
- **约束 / SDC（Synopsys Design Constraints）**：一个文本文件，用 Tcl 语法告诉工具"时钟多快、哪些路径不用管、引脚接在哪、输入输出延迟多少"。安路工具用的是同一套语法。
- **时钟域（Clock Domain）**：由同一个时钟驱动的所有寄存器，算一个"域"。跨域传信号叫**跨时钟域（CDC, Clock Domain Crossing）**，是 FPGA 设计里最容易出错的地方。
- **异步（Asynchronous）**：两个时钟之间没有固定相位关系（比如一个是 50 MHz 晶振来的，另一个是摄像头来的）。
- **伪路径（False Path）**：结构上存在、但实际永远不会按那个时序要求工作的路径。声明它是伪路径，就是告诉工具"别检查它"。
- **时序例外（Timing Exception）**：`set_clock_groups`、`set_false_path`、`set_multicycle_path` 这类"修改默认检查规则"的约束统称。
- **io 约束 / 引脚约束**：告诉工具"哪个信号接到芯片的哪个物理管脚、用什么电平标准"。你的引脚约束在 `user_source\constraints_source\pin.adc`（1,415 字节），里面能看到 `IOSTANDARD TMDS33`——那是 HDMI 输出的电平标准。

**名词解释**
- **MIPI CSI-2**：摄像头输出图像的**接口协议标准**。（CSI = Camera Serial Interface）
- **D-PHY**：MIPI 用的**物理层**（电平、差分对、时钟）。你的芯片里是**硬核**（芯片出厂就做好的专用电路，不占 LUT）。
- **Lane（通道/车道）**：MIPI 用几对差分线并行传数据，一对就是 1 lane。你的配置是 **2 lane**。
- **RAW10 / RAW8**：摄像头**没有做色彩处理**前直接输出的原始数据格式，10 bit 或 8 bit 一个像素。每个像素只有一个颜色分量（Bayer 阵列）。
- **Bayer 阵列 / 去马赛克（Demosaic）**：传感器上每个像素点前面盖一片红、绿或蓝的滤光片，所以每个点只知道一种颜色。**去马赛克**就是根据邻居推测出缺失的另外两个颜色。你的 `demosaic` 模块参数是 `BAYER_MODE "BGGR"`（B-G-G-R 排列）。
- **AWB（Auto White Balance，自动白平衡）**：让白色物体在图像里真的是白色，不受灯光颜色影响。原理是分别算 R/G/B 的平均值，然后算增益去乘。
- **ISP（Image Signal Processor，图像信号处理器）**：一整套图像处理流水线的统称。典型步骤：黑电平校正 → 去马赛克 → 白平衡 → 色彩校正 → Gamma → 锐化……
- **AXI-Stream**：一种标准的**数据流接口**（有数据有效信号、握手信号，没有地址）。视频流常用它。
- **帧缓存（Frame Buffer）**：把一整帧图像先存进内存再读出来。作用是**解耦输入输出速率**（摄像头来的和 HDMI 要的节奏不一样）和**做帧率转换**。
- **DDR2**：板子上那颗外部内存芯片，容量大但比片上 RAM 慢得多。你的设计用它存图像帧。
- **TMDS（Transition Minimized Differential Signaling）**：HDMI 用的**物理层编码方式**。HDMI 线上跑的就是 TMDS 信号。
- **VTC / 视频时序控制器**：产生"这一行从哪开始、这一帧有多少行、什么时候发同步信号"的模块。
- **I2C**：一种两线（SCL 时钟 + SDA 数据）**慢速配置总线**，用来给摄像头写寄存器。

**名词解释**
- **在线调试 / 片上逻辑分析仪**：把一段"采集逻辑"也综合进 FPGA，运行时把内部信号的波形存在片上 RAM 里，再通过 JTAG 读回电脑看。安路的叫 **ChipWatcher**（Xilinx 的叫 ILA，Intel 的叫 SignalTap）。

**注意（重要）**：加调试探针后**必须重新综合和布局布线**，而且会影响时序和面积。所以最干净的做法是：**先跑一版不含探针的工程确认功能，再跑一版含探针的用于调试。**

| 时序 | "这活儿在一个时钟节拍内干得完吗？" |

| 关键路径 | Slack 最小的那条路 |
| STA | 静态时序分析，**不跑仿真**，按延迟算全部路径 |
| CDC | 跨时钟域传信号，最容易出错的地方 |

| 步骤 | 做什么 | 为什么/注意 |
|---|---|---|
| 1 | **先别插摄像头**，只上电板子，看电源指示灯 | 万一分不清是板子问题还是摄像头问题，先排除一半可能 |
| 2 | 上电前用万用表量电源对地**没有短路** | 保命动作 |
| 3 | 装 JTAG 驱动（A7 的流程）：`UsbDriverTool.exe` → `FT_Prog.exe` → 拔插 USB | 装不对后面全做不了 |
| 4 | TD 里连上 JTAG，**点 `Scan`/`Detect`，确认能识别到 PH1P35 芯片** | 能识别到 = 驱动和链路 OK |
| 5 | 下载 `best_result\camera_to_dsi_display.bit` | 先跑商家的、已验证过的比特流，**不要先下自己改的** |
| 6 | **HDMI 线接显示器**，看有没有画面 | 这一步能出画面，说明整条通路通了 |
| 7 | **断电**，再接摄像头，再上电 | 摄像头带排线，**断电插拔** |
| 8 | 看画面：有没有图像？颜色对不对？ | 有图像 = 大成功 |
| 9 | 如果画面花屏/闪烁 → **先怀疑时序和 DDR**，不要急着改 ISP 算法 | 见下方排查表 |
| 10 | 出问题就上 **ChipWatcher**（顶层已有 `S_dbg_raw10_seen` 探针可用） | 抓 `raw10` 有没有数据进来，一秒定位是"没数据"还是"数据错" |

**最小排查表**

| 现象 | 首先怀疑 | 怎么验证 |
|---|---|---|
| 显示器无信号 | 比特流没下进去 / HDMI 线 / 分辨率不支持 | 换线、换显示器、重新下载 |
| 有信号但全黑 | 摄像头没出数据 / I2C 配置没成功 | ChipWatcher 抓 `S_dbg_raw10_seen` |
| 花屏、彩色噪点 | DDR 读写 / 跨时钟域 | 查 DDR 校准是否完成；看是否只有部分区域花 |
| 颜色不对（偏色） | AWB / Bayer 顺序（`BAYER_MODE`） | 换 `BAYER_MODE` 试（BGGR/RGGB/GRBG/GBRG） |
| 画面撕裂、滚动 | 帧同步 / VTC 时序 | 对比 VTC 输出的 H/V 参数和 720P60 标准值 |
| 整屏偏绿或偏紫 | 位宽转换（128↔96）对齐 | 看 `data128_96` / `data_96bit_to_128bit` |
