## 1. 选题解读

### 1.1 一句话理解题目

> 用一块 **集成度极高**（FPGA 逻辑 + RISC-V 硬核 + 512Mb 片内 DDR + 2 个 MIPI D-PHY 硬核）的安路 FPGA，把 **MIPI 摄像头的视频** 实时接进来，在 FPGA 里做 **图像算法**，叠加 **OSD 文字/图形和"安路"Logo**，再实时输出到 **HDMI 显示器**；在此基础上叠加能体现实时性、稳定性和实际应用价值的创新功能。

题目的关键词不是"算法"，而是 **"实时" + "完整通路" + "稳定"**。评分标准里"系统稳定性""展示效果"占了很重的分量——**通路稳定性优先于算法炫技**。

### 1.2 平台底账：先认清你手上有什么牌

PH1P35MDG324 关键资源（据安路官方选型表）：

| 资源 | 数值 | 对设计的真实含义 |
|---|---|---|
| LUT4 | 38,189 | 中等规模。通路（MIPI RX + DDR 控制器 + HDMI TX）可能吃掉 40%–60%，**算法能用的预算要先测出来** |
| DFF | 42,432 | 注意 LUT:FF ≈ 1:1.1，流水线打拍要省着用 |
| 分布式 RAM | 507 Kb | 小，做小 FIFO/查找表 |
| 块 RAM (ERAM) | 108 块 × 20Kb = **2,160 Kb ≈ 270 KB** | **放不下整帧图像！** 720p RGB888 一帧 = 2.76 MB。ERAM 只能做：行缓存、跨时钟 FIFO、字库 ROM、小窗口缓存 |
| DSP | 40 个（27×18 / 9×9） | 做 3×3 卷积够用（尤其只处理灰度单通道时），但**不能**做深度网络 |
| PLL | 6 | 够用：像素时钟、DDR 时钟、控制时钟各一个 |
| **MIPI D-PHY 硬核** | **2 个，v2.0，最高 2.5 Gbps/Lane** | **巨型红利**：D-PHY 物理层不用自己做（自己做几乎不可能）。你只需要做 CSI-2 协议层/对接官方 IP |
| **片内集成 DDR** | **1066 Mbps × 16 bit = 512 Mb ≈ 64 MB** | **第二红利**：不需要外部 DDR 芯片。理论带宽 2.13 GB/s，实际可用按 50%–70% 估 ≈ **1.0–1.5 GB/s** |
| RISC-V MCU 硬核 | 1 个 | 做 I2C 摄像头配置、按键/串口交互、机电联动控制，**不占逻辑资源** |
| 外部存储接口 | DDR2/3/4 @800 Mbps ×16 | 板载若有无均可，优先用片内 DDR |
| 用户 IO | 50 | 偏少，外扩板/按键/LED 要精打细算，注意引脚复用与原理图核对 |
| 收发器 | 无 HXT | **HDMI 必须靠 LVDS/TMDS 差分 IO 实现**（720p60 每 Lane 742.5 Mbps < LVDS 1.25 Gbps 上限，可行），或依赖板载发送芯片 |

**由此推出的三条硬约束**
1. **分辨率/帧率选 1280×720@60Hz 作为主目标**（题目也建议显示器支持 720p60）。1080p 作为挑战项。
2. **必须用片内 DDR 做帧缓存**，ERAM 只做行缓存/FIFO/字库。
3. **算法必须是"流式 + 小窗口"型**（Sobel、阈值、帧差、形态学、直方图统计），不能是"整帧迭代"或"大网络"型。

### 1.3 带宽预算（先算账，再设计）

以 **720p60、RGB888、24 bit** 计算：

| 项目 | 计算 | 结果 |
|---|---|---|
| 像素时钟 | 1280×720@60 标准 CVT 时序，总 1650×750 | **74.25 MHz** |
| 有效像素率 | 1280×720×60 | 55.3 Mpx/s |
| 视频净带宽 | 74.25 M × 24 bit | 1.782 Gbps |
| 每 Lane TMDS 速率 | 74.25 M × 10 | **742.5 Mbps** |
| DDR 写 + 读（1 帧缓存） | 1.782 × 2 | ≈ 3.56 Gbps ≈ **445 MB/s** |
| DDR 余量 | 1.0–1.5 GB/s 可用 − 0.45 GB/s | 充足，可支持帧差（2 读 1 写）、多算法并行取数 |

**关键洞察**：`1080p30`（像素时钟同样 74.25 MHz）与 `720p60` **带宽完全相同**，但每帧像素多 2.25 倍。所以如果算法需要整帧数据（帧差、直方图、连通域），**1080p30 反而比 720p60 更省心**；要展示"流畅度"则选 720p60。这也解释了为什么题目的显示要求只写到 720p60。

### 1.4 要求 → 功能清单（这是你后面所有工作的锚点）

给每条要求编个号，之后每个模块、每次验收都对应到编号。

### 1.5 评分标准拆解与得分策略

原文要点：基础扩展项与高阶挑战项**不设固定分值**，按"技术难度 + 完成质量"评；完成 1 项扩展得一定分，完成 2 项且效果良好可得扩展部分一半以上；**多项高阶 + 稳定 + 展示突出 = 高分甚至接近满分**；综合看**数量、难度、实时性、质量、稳定性、现场展示**。

**最优得分结构（推荐目标）**

```
基础 4 项（F1–F5）           → 100% 稳定，这是及格线和一切的前提
+ 基础扩展 2 项（F6、F7）     → 做扎实，不要半成品
+ 高阶挑战 3 项（H1、H3、H4）  → 性价比最高的三项
+ 1 个真实应用场景包装（F8）   → 让评委看到"有实际应用价值"
+ F9 的量化数据（资源/时序/延迟表）
= 目标：高分档
```

**三条得分心法**
1. **不做半成品**：宁少做一项，不做"能演示但会崩"的功能。评分明确写了"稳定完成 1 项即可得分"，崩掉的第三项是负分。
2. **效果 > 难度**：评委看的是显示器。**"左右分屏对比（左原图 / 右处理图）"** 是投入产出比最高的一个功能，务必做。
3. **用数据证明"实时"和"稳定"**：报告里放 **资源占用表 + 时序报告 Fmax + 实测端到端延迟 + 连续运行时长**。绝大多数队伍只会写"实现了某某算法"。

## 2. 总体思路与关键准备

### 2.1 三条铁律

| 铁律 | 含义 | 违反的后果 |
|---|---|---|
| **① 先通路，后算法** | 第一步目标永远是"摄像头 → HDMI 直通（passthrough）"，一个算法都不加 | 一上来写 Sobel，结果画面全黑，你分不清是算法错还是 MIPI 没通、DDR 没通、HDMI 时序错 |
| **② 先仿真，后上板** | 每个算法模块必须有 testbench + 参考模型逐像素比对通过，才允许上板 | 上板波形看不到内部信号，靠猜调试，效率降低 10 倍 |
| **③ 先稳定，后炫技** | 任何新功能合入前，先回答"它会不会让系统变得不稳定" | 演示当场花屏，前面所有工作归零 |

**三种缓存方案对比（P2 阶段必须做出选择）**

| 方案 | 结构 | 延迟 | 适用 | 建议 |
|---|---|---|---|---|
| A. 纯流式 | 行缓存 + 弹性 FIFO，不过 DDR | < 1 行（微秒级） | 灰度/Sobel/阈值等点/邻域算法 | 延迟最低，但**摄像头与显示时钟异步时容易撕裂**，需要 FIFO 深度匹配帧率差 |
| B. 单帧缓存（乒乓）| DDR 双缓冲 | 1–2 帧（16–33 ms @60fps） | 通用，解耦采集/显示时钟 | **推荐主方案**。撕裂彻底消除，也给帧差留了空间 |
| C. 多帧缓存 | DDR 三缓冲 / 多帧队列 | 2–3 帧 | 帧差、运动检测、延时测量 | 在 B 基础上加一路读，成本低，**为 H3/H4 铺路** |

> **强烈建议**：直接按 **方案 B/C**（乒乓缓冲）设计。虽然比 A 多 1–2 帧延迟（16–33 ms 完全满足"实时"），但它一次性解决了时钟异步、撕裂、帧差 三个问题。而且**延迟可测量**，正好做 H3 加分项。

### 2.3 关键决策表（P2 阶段逐项拍板并记录理由）

| 决策点 | 候选 | 推荐 | 理由 |
|---|---|---|---|
| 分辨率/帧率 | 720p60 / 1080p30 / 1080p60 | **720p60 主，1080p30 备** | 匹配题目建议的显示器；1080p30 同带宽但整帧算法更方便 |
| 像素格式 | RAW10→RGB888 / YUV422 | **内部统一 YCbCr444 或 RGB888 24bit** | 算法在 Y 通道做，色度直通，省 DSP 和 ERAM |
| 缓存方案 | A / B / C | **B 或 C** | 见上表 |
| I2C 配置由谁做 | FPGA 逻辑 / RISC-V MCU 硬核 | **MCU 硬核**（或先用逻辑，后期迁到 MCU） | 不占逻辑资源，方便改参数（曝光/增益，为 H5 铺路） |
| MIPI 协议层 | 官方 IP / 自研 | **官方 IP 优先**，自研仅做对接层 | 自研 CSI-2 不现实，时间要花在算法上 |
| HDMI 发送 | 自写 TMDS 编码 + OSERDES / 板载芯片 | **以原理图为准**，先找官方/厂商 HDMI 例程 | 决定你写多少代码 |
| 算法通道数 | 单路 / 多路并行 | **多路但同一时刻只跑一路 + 按键切换（H1）** | 资源有限，多路并行会爆 LUT/DSP |
| 演示形态 | 全屏处理图 / 分屏对比 | **按键切换：原图 / 处理图 / 分屏** | 分屏对比最直观，评分友好 |

**交付物**
- `docs/00_环境与工具流程.md`（含截图）

### 阶段 P1 · 需求分析与指标定义

**周期**：W3–W6
**目标**：把"题目文字"变成"可测量、可验收的技术指标"，并写出第一版演示脚本。

**关键任务**
1. **写《需求 → 指标 → 验证方法》三列表**。例：

| 需求 | 可量化指标 | 验证方法 |
|---|---|---|
| F1 MIPI 采集 | 720p60，无丢帧，连续 2h 丢帧率 < 0.01% | 帧计数器 + 错误计数器读回；跑机 2h 记录 |
| F2 HDMI 输出 | 720p60，显示器识别无异常，无闪烁 | 长时间观察 + 录屏 |
| F3 图像算法 | 灰度/二值/Sobel 任 1 种，处理图与原图差异可辨 | 分屏对比截图 |
| F4 系统稳定 | 连续 2h 无花屏；光照突变（开灯/遮镜头）不崩 | 老化测试记录表 |
| F5 OSD | 含"安路"Logo + 至少 1 行文字，位置可调 | 截图 |
| F9 性能 | 资源占用表 + Fmax + 端到端延迟实测值 | 综合/时序报告 + 延迟测试模式 |
| H1/H3/H4 | 切换平稳无黑屏；延迟以帧数可视化；运动区域计数正确 | 现场演示 + 录像 |

2. **确定分辨率/帧率与显示时序**，查表得到全部时序参数（HActive/HFP/HSync/HBP, VActive/VFP/VSync/VBP, 极性）。
3. **写"演示脚本 v1"**：现场 3–5 分钟怎么讲、按哪个键、屏幕上应出现什么、说什么话。**倒推功能优先级**——演示里讲不到的就不做。
4. **风险清单 + 对策**（见 §6）。
5. **对标调研**：搜 3–5 个同类开源项目/往届作品，记录它们的架构与踩坑，避免重复造轮子。

**工具与方法**
- 视频时序参数：查 CVT / CEA-861 标准表；或用 Python 小脚本生成时序参数表。
- 需求管理：一个 Markdown 表格就够，不要上重型工具。

**交付物**：`docs/01_需求与指标.md`、`docs/02_演示脚本_v1.md`、风险清单

**出口条件**：每条 F/H 都有量化指标和验证方法；演示脚本能被一个外人看懂并复述。

**常见坑**
- 只写"实现边缘检测"，没写"什么分辨率、多少帧、什么效果" → 最后无法验收，也无法优化。
- 忽略"光线剧烈变化时工作正常"这条稳定性评分 → 演示时一开灯算法就失效。
- 一开始就定 1080p60 这种高目标 → 后期带宽/资源双双爆掉。

**重点学习**：`[K7]` 视频时序与像素时钟 ★★★、`[K18]` 系统测试与指标测量 ★★

### 阶段 P2 · 方案设计与架构选型

**周期**：W6–W10
**目标**：产出**一张能落地的系统框图 + 一张数据流图 + 一张资源/带宽预算表**，并完成关键决策。

**关键任务**
1. 画 **系统框图**（模块 + 时钟域 + 数据宽度标注）和 **数据流图**（谁产生、谁消费、速率多少）。
2. 做 **时钟架构设计**：列出全部时钟域、频率、来源、相互关系；标出每一处跨时钟边界和所用同步手段（异步 FIFO / 握手 / 双口 RAM）。
3. 做 **带宽与存储预算**（用 §1.3 表格，填入自己的参数）。
4. 做 **资源预算**（§2.4 表格初版）。
5. **搭空壳通路工程**，跑通综合 + 布局布线，得到**资源与时序基线**。这一步是本阶段最重要的动作。
6. 逐项填写 §2.3 关键决策表，**写清理由**（答辩时会被问"为什么这么选"）。
7. **算法选型**：从 §4 路线图里挑出目标组合，明确每个算法的输入输出格式与资源量级。

**工具与方法**
- 画图：draw.io / Visio / PowerPoint（**别用花哨工具，能改就行**）。
- 时序预算：手算 + 表格；关键路径心里要有数。
- IP 复用评估：TD 的 IP 生成器里看有哪些现成 IP（FIFO、PLL、ROM、存储控制器等）。

**交付物**
- `docs/03_系统架构设计.md`（框图 + 数据流图 + 时钟表 + 带宽表 + 决策表）
- `docs/04_资源与时序基线.md`（空壳工程综合报告截图）
- 空壳工程可下载运行（HDMI 出彩条）

**出口条件**
- 空壳工程综合通过、时序收敛、板上 HDMI 正常显示。
- 你明确知道**算法还能用多少 LUT/ERAM/DSP**。
- 每一个跨时钟边界都有明确方案。

**常见坑**
- **跳过空壳基线直接写算法** → 后期发现 LUT 不够，架构要推倒重来（最常见的致命错误）。
- 时钟域没理清 → 后期随机花屏，查一周查不出。
- 选了"整帧迭代型"算法（如复杂 Canny、大卷积核）→ 在 38K LUT / 40 DSP 上做不出来。
- 分辨率没参数化 → 改分辨率要动几十个文件。

**重点学习**：`[K4]` 跨时钟域与亚稳态 ★★★、`[K9]` 存储与带宽、行缓存 ★★★、`[K2]` 资源类型与用量估算 ★★★、`[K8]` 视频接口协议概览 ★★

### 阶段 P3 · 模块划分与接口定义

**周期**：W10–W13
**目标**：把架构切成**可独立开发、可独立仿真、可独立上板验证**的小模块，并冻结接口。

**关键任务**
1. **写模块层次表**（建议如下，按自己情况调整）：

| 层次 | 模块 | 职责 | 关键接口 | 负责人 |
|---|---|---|---|---|
| L0 Top | `top.v` | 例化与连线，不含逻辑 | 全部 | A |
| L1 采集 | `mipi_rx_wrap` | D-PHY + CSI-2 对接，输出像素流 + 错误统计 | `pxl_data/pxl_valid/sol/eol/sof/eof` | A |
| L1 采集 | `cam_i2c_cfg` | 摄像头寄存器配置（初版逻辑实现，后迁 MCU） | I2C SCL/SDA | C |
| L1 缓存 | `frame_buffer` | 乒乓/三缓冲，DDR 读写调度 | 写口/读口 | A |

| L1 显示 | `hdmi_tx` | TMDS 编码 + 串化 | 差分对 | A |
| L2 前处理 | `bayer2gray` / `yuv2rgb` | 格式与位宽转换 | 像素流 | B |
| L2 前处理 | `line_buffer_3x3` | 行缓存 + 3×3 窗口生成 | `win[8:0]` | B |

| L2 算法 | `stat_engine` | 直方图/阈值/运动像素计数统计 | 计数寄存器 | B |

**交付物**：`docs/05_模块划分与接口手册.md`、`docs/06_寄存器手册.md`、工程目录骨架、各模块空壳 + 空 testbench

### 阶段 P4 · 分模块编码实现

**周期**：W13–W24（与 P5 并行推进）
**目标**：按模块逐个实现，**每个模块写完立即仿真**，绝不攒着一起调。

**实现顺序（严格按此顺序，前一个不通不做下一个）**

```
① video_timing_gen  → ② hdmi_tx       ← 先点亮显示器（彩条），建立信心与基线
③ test_pattern      → ④ mipi_rx_wrap   ← 让真实画面进得来（先直通显示）
⑤ frame_buffer      → ⑥ 端到端直通 DONE ← 【里程碑】不做算法，先有稳定直通
⑦ preprocess + line_buffer_3x3
⑧ algo_gray → algo_bin → algo_sobel    ← 基础 F3
⑨ osd_overlay + 字库 + Logo            ← 基础 F5
⑩ algo_mux + 按键 + 状态 OSD           ← H1
⑪ stat_engine + 帧差 algo_framediff    ← H4
⑫ latency_meter                        ← H3
⑬ 颜色分割 + 包围盒 + 坐标叠加          ← H2
⑭ 风格化（边缘+填充）/ 形态学           ← F6
⑮ 目标检测/分类 + 文字说明              ← F7
⑯ 串口/舵机联动                        ← F8
⑰ 自动曝光/白平衡/直方图均衡            ← H5
```

**各模块编码要点**

| 模块 | 要点 | 易错 |
|---|---|---|
| `video_timing_gen` | 行/场计数器，产生 `hs/vs/de` 与 `x/y` 坐标；参数化；复位后第一帧要完整 | 极性搞反（显示器不认）；x/y 与 de 不对齐（图像偏移/黑边） |
| `hdmi_tx` | TMDS 8b/10b 编码（含 DC 平衡）+ OSERDES 10:1 串化 + 差分输出；三路数据 + 一路时钟 | 编码表写错（花屏/偏色）；串化时钟相位；未做 DC 平衡（长线不出图） |
| `mipi_rx_wrap` | 复用官方 IP；重点写"协议层 → 像素流"的对接与错误统计 | 字节序/位序搞反（颜色错）；Lane 映射错；忘了统计 CRC/ECC 错误 |
| `frame_buffer` | 乒乓写读切换在**帧消隐期**完成；地址用 `{frame, y, x}`；注意 DDR 突发对齐 | 切换时刻落在有效像素区 → 撕裂；读写冲突 → 花屏；地址位宽不够 |
| `line_buffer_3x3` | 用 2 个（或 3 个）行缓存 + 移位寄存器组生成 9 像素窗口；用 ERAM 而非寄存器 | **行首/行尾/帧首/帧尾的边界处理**（最高频 bug）；行缓存深度算错 |
| `bayer2gray` | 取 G 通道或加权平均；注意 Bayer 相位（RGGB/BGGR） | 相位选错 → 图像变灰但细节异常/伪彩 |
| 各算法 | 统一"输入像素流 → 输出像素流 + 参数寄存器"接口；**定点化**；溢出用饱和不用回绕 | 位宽溢出/截断错误 → 异常条纹；除法用移位近似但忘了精度损失 |
| `osd_overlay` | 字库 ROM（ERAM 初始化）；Alpha 混合 `(fg*a + bg*(255-a))>>8`；位置寄存器化 | ROM 初始化文件格式/位宽错；Alpha 除 256 写成除 255；OSD 与视频时钟不同步 |
| `reg_file` | 简单寄存器组 + 读写接口；跨时钟用双口或握手 | 多 bit 跨时钟直接采样 |
| `stat_engine` | 直方图/计数在帧消隐期清零与锁存；计数位宽要够 | 计数器溢出；清零时机与读出冲突 |

**工具与方法**
- TD 综合 + 布局布线；每完成一个模块综合一次，记录资源变化。
- ModelSim 仿真该模块的 testbench。
- **Python 参考模型**：先用 NumPy/OpenCV 实现同一算法，生成 `expected_*.txt`，与仿真输出逐像素 diff。**这是本阶段最高效的手段。**
- Git 分支：每个模块一条分支，仿真通过后合并到 `dev`。每个模块至少一个 commit，写清"实现了什么、验证到什么程度"。

**交付物**：各模块 RTL + testbench + 仿真报告；每个模块的"功能 与 验证状态"矩阵

**出口条件**
- 每个模块**单独仿真通过**（含边界用例）。
- 端到端直通（⑤⑥）在板上稳定运行 30 分钟。
- 基础 F3（至少一种算法）与 F5（OSD + 安路 Logo）在板上可见。

**常见坑（这一阶段 80% 的时间会花在这些上）**
- 位宽溢出/截断 —— 用 Python 参考模型对照，别靠眼睛看。
- 行首行尾边界 —— 测试向量必须覆盖 1×1、2×2、最窄宽度、非 2 的幂宽度。
- 复位与使能不同步 —— 仿真通过、上板随机错，典型 CDC 问题。
- 只测正常路径，不测"帧首帧尾/半帧/断流" → 上板遇到摄像头抖动就崩。
- 一个模块改完不重跑全量回归 → 改 A 坏 B。

**重点学习**：`[K1]` RTL 编码 ★★★、`[K3]` 状态机 ★★★、`[K4]` CDC ★★★、`[K9]` 行缓存与窗口 ★★★、`[K11]` 定点数与位宽 ★★★、`[K10]` 图像算法硬件化 ★★★、`[K12]` OSD 与字库 ★★、`[K14]` Python 自动化 ★★★

### 阶段 P5 · 仿真验证（与 P4 并行）

**周期**：W13–W26
**目标**：建立"**能自动跑、能自动判、能覆盖边界**"的验证环境。仿真不是走过场，它是你唯一能看清内部信号的地方。

**关键任务**
1. **搭三层验证环境**
   - 模块级：单模块 testbench，直接灌像素、检查输出。
   - 子系统级：如"前处理 + 行缓存 + 算法"，验证数据流贯通。
   - 系统级（可选）：简化版 MIPI 源模型 + DDR 行为模型 + HDMI 时序检查器。
2. **测试激励自动生成（Python）**：
   ```
   gen_vectors.py  →  sim/vectors/in_64x64.txt（含边界图案：全黑、全白、棋盘、
                      竖线、横线、单像素点、随机噪声、渐变）
   ```
   边界图案是抓边界 bug 的核心，**不要只用随机图**。
3. **参考模型自动比对（Python）**：
   ```
   仿真输出 out.txt  →  compare.py 与 OpenCV 结果逐像素 diff
                     →  输出"最大误差/误差像素数/PASS or FAIL"
   ```
   把 PASS/FAIL 做成脚本返回值，保证回归可自动化。
4. **写回归脚本**：一条命令编译所有 testbench + 跑全部用例 + 汇总报告（`.do` 脚本 + 批处理/Python）。
5. **构建时序与约束**：
   - 写 `top.sdc`：`create_clock`（像素时钟 74.25 MHz、DDR 时钟、控制时钟）、`set_input_delay/set_output_delay`、`set_clock_groups -asynchronous` 声明异步时钟组、必要的 `set_false_path`。
   - 每次布局布线后**读时序报告**：看 WNS/TNS、找关键路径、判断是否需要插流水线。
6. **静态检查**：综合警告（位宽不匹配、latch 推断、未连接端口、组合环）清零或逐条说明理由。
7. **后仿（可选但推荐）**：至少对 CDC 模块和复位逻辑跑一次带延迟的时序仿真。

**工具与方法**
- ModelSim/QuestaSim + 安路器件仿真库（原语、ERAM、PLL 模型）。
- 波形调试：**先看 valid/data 握手，再看数据**，比盯着数据流找错快得多。
- **上板抓帧成像法（强烈推荐）**：用 TD 在线逻辑分析仪抓一帧像素数据导出到文件，Python 还原成 PNG。**一眼就能看出错位、颜色错、边界黑边**，比看波形快 10 倍。这是很多队伍不知道的技巧。

**交付物**
- `sim/` 完整可跑的回归环境（一条命令出报告）
- `docs/07_仿真验证报告.md`：每个模块的用例、覆盖的边界、比对结果
- `constr/top.sdc` 时序约束 + 时序报告汇总

**出口条件**
- 一条命令跑完全部回归，结果 PASS/FAIL 明确。
- 每个算法模块与 Python 参考模型**逐像素一致**（或误差在明确说明的容差内）。
- 时序约束齐全，无未约束的时钟路径。
- 综合警告逐条有结论。

**常见坑**
- 只用理想激励（全图渐变）→ 边界 bug 全部漏到板上。
- testbench 里用 `#100` 硬等，不用握手信号 → 改时序就全崩。
- 没有自动判据，靠肉眼看波形 → 回归无法自动化，改一处要重看一晚。
- 忘记把输出 dump 出来做像素级比对 → 只能看波形猜。
- `set_clock_groups` 没写 → 工具去优化跨时钟路径，浪费资源还可能引入问题。
- 后仿不做，CDC 问题留到板上随机爆发。

**重点学习**：`[K6]` 验证方法与 testbench ★★★、`[K5]` 时序约束与 STA ★★★、`[K14]` Python 自动化比对 ★★★、`[K4]` CDC 验证 ★★★

### 阶段 P6 · 上板调试与系统集成

**周期**：W18–W30
**目标**：把一堆"仿真通过"的模块，变成一个"连续 2 小时不崩"的系统。

**集成顺序（一次只加一样东西）**

```
1. 彩条显示            → 稳定 10 min
2. + OSD（静态 Logo）  → 稳定 10 min
3. + 摄像头直通        → 稳定 30 min   ← 此时应该看到"活的画面"
4. + 帧缓存（乒乓）    → 稳定 30 min   ← 撕裂消失
5. + 灰度              → 稳定 30 min
6. + 二值化/Sobel      → 稳定 30 min
7. + 按键切换 + 状态OSD
8. + 帧差/统计/延迟测量
9. + 机电联动 / 串口
10. 全功能跑机 2h + 光照突变测试 + 老化 12h
```

**调试方法（按此优先级）**
1. **分步点亮法**：任何新问题，先回到"上一个确定能工作的状态"，再逐步加回。不要在全功能工程上猜。
2. **二分法定位**：把数据通路从中间切开，用 `test_pattern` 替换前半段，看后半段是否正常 → 快速确定问题在采集侧还是显示侧。
3. **计数器与状态寄存器**：`fifo_overflow_cnt`、`frame_cnt`、`line_cnt`、`crc_err_cnt`、`pll_locked`、`state`。**把它们定期打印或显示在 OSD 上**（自制的"仪表盘"），是稳定性问题的唯一靠得住的手段。
4. **在线逻辑分析仪（TD 内嵌调试工具，具体名称以所用 TD 版本为准）**：抓关键握手信号；注意深度有限，要设好触发条件（如"帧首 + 数据异常"）。
5. **抓帧成像**：见 P5。
6. **示波器**：确认 MIPI 差分有信号、HDMI 时钟频率正确、电源纹波正常。

**上板调试高频故障速查（详细版见配套《排错手册》）**

| 现象 | 最可能原因 |
|---|---|
| 显示器完全黑屏/无信号 | HDMI 时钟未输出、TMDS 编码错、引脚约束错、显示器不支持该分辨率 |
| 有信号但花屏/雪花 | TMDS DC 平衡/编码错、串化时钟相位、差分对约束错 |
| 画面偏色（整体发红/发蓝） | 通道映射错、Bayer 相位错、RGB↔YCbCr 量化范围错（全范围 vs 有限范围） |
| 画面撕裂/上下错位 | 帧缓存乒乓切换时机不在消隐期；采集/显示时钟未解耦 |
| 边缘有黑边/竖条纹 | 行缓存边界处理错、像素计数与 DE 不对齐 |
| 偶发花屏（几秒钟一次） | **CDC 问题**、复位未同步、FIFO 深度不足、供电不稳 |
| 上电有时能显示有时不能 | PLL 未 lock 就释放了逻辑复位；上电时序 |
| 运行几分钟后失效 | 温度/散热、电源、DDR 时序余量不足 |
| 一开灯/变换光照算法失效 | 固定阈值算法 + 无自动曝光；演示脚本要预置处理 |

**稳定性专项测试（F4 的验收证据，务必留档）**
- [ ] 连续运行 **2 小时**，每 15 分钟截屏记录一次，记录帧计数与错误计数。
- [ ] **光照突变测试**：遮挡镜头 / 手电照射 / 开关灯，观察是否恢复。
- [ ] **热插拔与复位测试**：HDMI 拔插、按复位键 20 次，观察是否每次都能正常启动。
- [ ] **上电自启测试**：下载到 Flash，断电再上电 10 次，检查是否每次自启成功（**现场演示必须靠这个**）。
- [ ] **老化测试 12 小时**（有条件），记录有无异常。

**工具与方法**
- TD 在线调试/逻辑分析仪；串口输出日志；OSD 上的自制"仪表盘"。
- 录像记录每次实验（**这也是答辩素材**）。

**交付物**

- `docs/08_上板调试日志.md`（问题 → 定位方法 → 根因 → 解决 → 验证，**这份文档直接变成报告里的"测试与调试"章节**）

**出口条件**
- 全功能系统连续 2 小时无花屏、无溢出、无丢帧异常。
- Flash 固化后断电重上电 10/10 成功自启。
- 基础 4 项 100% 达标；目标的扩展/高阶项全部可见。

- 没有错误计数器，稳定性问题无法量化、无法复现。

### 阶段 P7 · 优化与性能提升

**周期**：W24–W36
**目标**：用**数据**证明"实时、低资源、稳定"，拿下 F9 与"性能优化与创新"的分数。

**四个优化方向（按优先级）**

| 方向 | 手段 | 证据 |
|---|---|---|
| ① 时序收敛 | 关键路径插流水线；减少组合逻辑级数；`(* keep *)`/寄存器复制；重定时；必要时降一点算法并行度 | WNS ≥ 0 且余量 > 10%；报告 Fmax |
| ② 资源优化 | 多算法**时分复用**同一套乘法器/DSP；用移位代替乘除；位宽按需收窄（如 Y 通道 8 bit）；行缓存用 ERAM 而非寄存器；常量系数用 CSD 编码 | 优化前后资源占用对比表 |
| ③ 延迟优化 | 减少缓存的帧数（三缓冲→乒乓）；算法流水线级数最少化；避免不必要的整帧往返；旁路路径（流式直通模式） | 实测端到端延迟（毫秒 + 帧数） |
| ④ 带宽优化 | 只搬运必要数据（灰度单通道）；DDR 访问合并成突发；提高有效数据占比；帧缓存用 16bit（RGB565/YCbCr422）代替 24bit | 带宽占用计算 + 实测 |

|---|---|---|---|
| LUT4 | | | |
| DFF | | | |
| ERAM | | | |
| DSP | | | |
| Fmax（最差路径） | | | |
| 端到端延迟（ms / 帧） | | | |
| 支持帧率 | | | |
| 连续稳定运行时长 | | | |

**工具与方法**
- TD 时序报告、资源报告、功耗估算；逻辑分析仪测延迟；Python 处理日志与画对比图。
- **延迟测量方案（H3）**：在采集侧给每帧打一个递增的帧号（或计数器时间戳），写进帧缓存的隐藏行/像素，显示侧读出来做差 → 得到"采集到显示经过了多少帧/多少毫秒"，再把结果显示在 OSD 上。**这是最优雅的加分项实现方式。**

**交付物**：`docs/09_性能优化报告.md`（含上表 + 关键路径截图 + 延迟测量原理与数据）

**出口条件**：所有指标有实测数据；时序有 ≥10% 余量；系统在目标帧率下无丢帧。

**常见坑**
- 只做功能不做优化，报告里没有性能数据 → 直接丢掉"性能优化"分。
- 为了优化把功能改坏（**每次优化后重跑全量回归**）。
- 延迟只写"很低"没有实测值。
- 时序靠"能跑就行"，余量为 0 → 换个批次芯片/温度高一点就崩（评审现场可能就是这样）。

   - 如果光线剧烈变化 / 摄像头断流，系统怎么表现？
5. **演示环境检查表**：显示器、HDMI 线（合规 ≤5 m 纯铜）、电源、备用排线、备用下载器、笔记本（预装工程与视频）、U 盘备份、螺丝刀/扎带、延长线插排。

**交付物**：技术报告、PPT、演示视频、现场演示脚本、答辩 Q&A 手册、代码仓库（含 README 与一键复现说明）

**出口条件**：3 次彩排全部成功；任何一次彩排失败都要定位并解决后再算通过。

**常见坑**
- 文档最后一周才开始写 → 无法回头补数据（**数据必须边做边记**）。
- 报告只有"实现了什么"，没有"为什么这么选""效果如何量化"。
- PPT 塞满文字和代码；评委看不到效果。
- 只准备正常演示，没准备故障预案。
- 演示用设备与调试设备不同（换显示器/换线）→ 现场翻车。
- 忘记把工程/视频备份到 U 盘和云端。

**重点学习**：`[K18]` 技术表达与数据呈现、`[K15]` 版本控制与工程归档

## 4. 图像算法路线图（按"得分 / 工作量"排序）

下表是**推荐的实现顺序**。原则：先做不占资源、效果直观、复用已有硬件的。

| 序 | 算法 | 归属 | 难度 | 资源量级 | 硬件实现要点 |
|---|---|---|---|---|---|
| 1 | 灰度变换（加权/取 G） | F3 | ★☆☆ | 极少 | 组合逻辑，注意 Bayer 相位 |
| 2 | 二值化（固定阈值 / 自适应阈值） | F3 | ★☆☆ | 极少 | 阈值寄存器化；自适应需局部均值 → 复用行缓存 |
| 3 | **Sobel / Prewitt 边缘检测** | F3、F6 | ★★☆ | 小（无需乘法） | 3×3 窗口 + 加减与移位（×1,×2）→ 无 DSP 消耗；**必做，效果最直观** |
| 4 | 高斯/均值滤波 | F6 | ★★☆ | 中（9 乘法/像素） | 系数对称可复用乘法器；只处理 Y 通道省 2/3 |
| 5 | 形态学腐蚀/膨胀 | F6 | ★★☆ | 小 | 3×3 min/max 比较树 |
| 6 | 色彩空间 RGB↔YCbCr、RGB↔HSV | F6、H2 | ★★☆ | 中 | 定点系数；HSV 需除法 → 用查找表或比较式替代 |
| 7 | 直方图统计 + 均衡 | H5 | ★★★ | 中（BRAM 256×N） | 统计在消隐期清零/锁存；均衡用累加表查 LUT |
| 8 | **帧差法运动检测 + 区域计数/标注** | H4 | ★★★ | 中（需 3 帧缓存） | 帧缓存读两帧做差 → 阈值 → 投影统计 → 标注框；**推荐，得分高** |
| 9 | 中值滤波（3×3/5×5） | F6 | ★★★ | 中 | 排序网络，注意流水线级数 |
| 10 | 颜色阈值分割 + 连通域标记 + 包围盒 + 坐标输出 | F7、H2 | ★★★★ | 中高 | 连通域用两遍扫描或行程编码；**建议先做"投影法"求包围盒简化版** |
| 11 | 边缘提取 + 区域填充（卡通化/风格化） | F6 | ★★★★ | 中高 | 边缘检测 + 量化（色彩层级化）+ 边缘叠加；填充用形态学闭运算近似 |
| 12 | 简单目标分类（形状/尺寸判据） | F7 | ★★★★ | 中 | 用包围盒长宽比、填充率、面积做规则判据，**不做神经网络** |
| 13 | 自动曝光 / 白平衡闭环 | H5 | ★★★★★ | 中 | 统计亮度均值 → 通过 MCU 改摄像头曝光/增益寄存器（**用 RISC-V 硬核，不占逻辑**） |

**两套推荐组合**

- **保底组合（保证基础分，约 6 周工作量）**：1 + 2 + 3 + 9（OSD）
- **冲高组合（目标高分，约 16 周工作量）**：保底组合 + 6 + 8 + 10(投影法简化版) + 11 + 按键切换 + 延迟可视化 + 串口/舵机联动

> **资源省法**：所有算法只在 **Y（亮度）通道** 上做，色度通道直通。这样 DSP 与 ERAM 消耗直接降到 1/3，且主观效果几乎无损。这是本题目下最重要的一个实现技巧。
