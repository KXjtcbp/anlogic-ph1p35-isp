## 一、先读这一页（30 秒结论）

你的板子烧录后"屏幕全白"。这句话在排查上其实分成**两种完全不同的情况**，
它们的原因和修法毫无关系。**在动手改任何工程之前，必须先分清你是哪一种：**

| 类型 | 你看到的样子 | 含义 | 大致方向 |
|---|---|---|---|
| **A 类：纯白** | 整个屏幕纯白，**没有任何文字、图标、菜单、厂家 Logo** | 显示器**收到了有效信号**，但收到的像素数据恒为白色 | FPGA 内部数据通路问题 |
| **B 类：白底 + 文字** | 白底（或蓝底/黑底），**角落或中央有 "No Signal"、"无信号"、"检查信号线"、"不支持的分辨率" 等字样**，或显示器电源灯是**橙色/红色**而不是蓝色/白色 | 显示器**根本没收到有效信号**，白屏只是显示器自己的待机画面 | 信号/时钟/烧录/接线问题 |

> **为什么必须先分清？** 因为 B 类根本不用改 Verilog，多半是接线、烧录方式或时钟问题；
> 而 A 类说明 HDMI 输出链路是活的，要去查摄像头数据通路。方向完全相反。

**📌 现在请你做一件事**：重新看一眼屏幕，告诉我上面有没有文字、显示器电源灯什么颜色。
这决定了后面走哪条路。

### 2.5 ⭐ HDMI 像素时钟 75 MHz ≠ 标准 74.25 MHz（必须知道的偏差）

- 1280×720@60Hz 的 **CEA-861 标准像素时钟是 74.25 MHz**。
- 你的工程给的是 **75.000 MHz**（= 50 × 1.5）。
- **偏差 +1.01%**，等效帧率变成 60 × (75 ÷ 74.25) ≈ **60.61 Hz**。

**这意味着什么（通俗版）**：
HDMI 显示器靠"对方送来的时钟"来对齐画面。它在内部用一个锁相环（PLL）去"抓住"这个时钟。
±1% 的偏差，绝大多数显示器能抓住（一般能容忍 1%~2%），但**少数显示器、电视、采集卡会抓不住**。
抓不住的表现是：**黑屏 / 无信号 / 画面闪烁 / 画面横向滚动**——
注意：**它不会造成"纯白"**。所以这是"无信号类"故障的候选原因，不是"全白"的直接原因。

## 三、复现流程（从烧录到观察，逐步可记录）

> 目的：把"我烧了，白了"变成**一份可以被分析的记录**。
> 请按顺序做，**每一步把结果填进第 3.8 节的表格**。不要跳步。

### 第 1 步 · 确认比特流文件确实生成且是新的

在 TD 里或文件管理器里找到生成的比特流文件，记录：

- 文件路径（通常形如 `td_project\camera_to_dsi_display_Runs\phy_1\...bit` 或工程目录下的 `.bit` / `.fs`）
- 生成时间（是不是你刚刚这次布局布线的时间）
- 文件大小（**不为 0**）

> 依据：你之前的流程是 `reset_run syn_1 phy_1` → `launch_runs syn_1 phy_1` →
> `Run syn_1 success` / `Run phy_1 success` → `The implemented result of phy_1 is saved as best result.`
> 只要最后这句话出现过，比特流就是新的。

### 第 2 步 · 记录 TD 里的器件设置（最容易出错的一步）

打开 TD → 工程设置，确认并记录：

| 检查项 | 应该是 | 你的实际值 |
|---|---|---|
| Device | `PH1P35MDG324` | |
| Family | `PH1` | |
| Speed Grade | `-3` | |

> **为什么这条最致命**：如果器件选错（比如选成 PH1P35**B** 或别的封装），
> 生成的比特流**引脚位置映射完全不对**，烧进去之后所有引脚都在干别的事，
> 屏幕上自然什么都不会对。这是"烧了没反应"的头号原因之一。

> **【待你确认 · 重要】** 你的工作区里同时存在两份互相矛盾的资料：
> - `HX1P35B开发板引脚分配汇总.docx`
> - `HX1P35B_FT_40P_*.pdf` 原理图
> - `新HX1P35A开发板手册-HDL版2604.pdf`
> 而官方 Q&A 第 14 条明确写着"平台 2 = **HX1P35A**"。
> **请先确认你手上的板子到底是 HX1P35A 还是 HX1P35B**，
> 并确认板子上 HDMI 接口的 4 根 TMDS 差分对，是不是就接在 **G16 / F17 / H14 / C17** 上。
> 如果板子型号与 `pin.adc` 不符，那么引脚约束必须整份重做。**这是无法用软件绕过的。**

### 第 3 步 · 确认烧录方式：SRAM 还是 Flash？（初学者最常踩的坑）

TD 的下载工具里有不同的目标，务必看清你点的是哪个：

| 烧录目标 | 掉电后 | 说明 |
|---|---|---|
| **SRAM / JTAG 在线下载** | **程序消失！** | 只 Download 到 FPGA 内部 SRAM，**一断电就没了** |
| **Flash / 固化 / Program** | 保留 | 写进板上的配置 Flash，重新上电自动加载 |

**❗ 请回忆你的操作**：烧录完之后，你有没有**断过电**、**按过板子上的复位/重新配置按键**、
或者**重新插拔过 USB / 电源**？

- 如果**有** → 那"全白"极可能只是**程序已经丢了**（显示器无信号 → 白屏待机画面）。
  **这不是设计错误，是操作问题。** 重新下载一次并**保持不断电**，再看屏幕。
- 如果**没有**，程序还在跑，那才需要往设计里查。

### 第 4 步 · 记录硬件连接状态（断电→接线→上电）

1. **断电**
2. HDMI 线：**板子上的 HDMI OUT → 显示器的 HDMI IN**。
   - 换一根线试一次（HDMI 线内部断芯非常常见，尤其廉价的）
   - 换一个显示器试一次（如果手边有）
3. 摄像头：**确认排线插到底、方向没插反**（MIPI FPC 排线反插是最常见的物理故障）
4. **上电**
5. 记录板上指示灯：
   - 有没有 **PLL 锁定指示灯**（常叫 `LOCK` / `PLL_LOCK`）？亮不亮？
   - 有没有 **配置完成指示灯**（常叫 `DONE` / `CFG_DONE`）？亮不亮？
   - 电源灯是否正常？

### 第 5 步 · 观察并记录屏幕表现（关键）

**上电后等 10 秒**（显示器重新识别信号需要时间），然后记录：

- [ ] 屏幕是纯白，还是有文字？（A 类 / B 类）
- [ ] 显示器电源指示灯颜色（蓝/白 = 有信号；橙/红 = 无信号）
- [ ] 屏幕有没有一闪而过？还是稳定白着？
- [ ] 显示器 OSD 里显示的输入分辨率是多少？（如果有这个菜单，去看一眼，很有价值）
- [ ] 拔掉 HDMI 线，屏幕样子**有没有变化**？
      → **如果拔线和插线屏幕长得一模一样，说明 FPGA 根本没送信号出来。**

### 第 6 步 · 试一试按键

`pin.adc` 第 10–11 行说明板上有两个按键：`I_button[0]` = N2，`I_button[1]` = J14。

**逐个按一下，每个按 1 秒，观察屏幕有没有任何变化。** 记录按了哪个、屏幕怎么变。

### 第 7 步 · 断电重上电，再看一次

- 如果这次好了 → 说明是**上电时序/复位**问题，记录"第一次上电白、重新上电正常"。
- 如果还是白 → 记录。

| **A6** | 板上晶振频率 = **50 MHz** | SDC 第 1 行 `-period 20.000` | 晶振不是 50M → 全部时钟错，画面必定异常 |

**A5 详解（很重要，请一定看）**：

顶层代码 `design_top_wrapper.v` 第 488–490 行：

```verilog
PLL u_PLL(
    .refclk ( I_sys_clk ),
    .reset  ( ~I_rst_n  ),   // ← 注意这个取反
    ...
```

- PLL 的 `reset` 是**高电平有效**，接的是 `~I_rst_n`。
- `I_rst_n` 在 `pin.adc` 第 3 行绑到 **R10**，且设了 `PULLTYPE = PULLUP`（内部上拉）。
- **如果 R10 在板上是一个"按下为低"的按键**：不按时为高 → `~I_rst_n` = 0 → PLL 正常工作 ✅
- **如果 R10 在板上被下拉、悬空、或你一直按着它**：`I_rst_n` = 0 → `~I_rst_n` = 1 → **PLL 被永久复位** → 没有时钟 → 没有 TMDS 输出 → 屏幕无信号 ❌

**怎么做**：断电，用万用表蜂鸣档/电压档量一下 R10 这个网络在**不按键**时是高还是低；
或者直接翻你手上那份开发板原理图，找到 R10 那个网络名，看它接上拉还是下拉。
**这是"烧录后屏幕毫无反应"的第一嫌疑人。**

## 五、如果是 A 类（纯白）——数据通路排查决策树

> **再次强调**：纯白 = HDMI 输出链路是活的，问题在"送进 HDMI 编码器的像素数据恒为白"。
> 下面这个工具是**决定性**的，比反复烧板子有用一百倍。

### 5.1 ⭐ 用 `DEBUG_MODE` 一屏定位（最高优先级行动项）

工程自带一个自检开关。位置：`user_source\hdl_source\design_top_wrapper.v` **第 818 行**：

```verilog
.DEBUG_MODE ( 0    ) // Normal SC500 1280x720 camera image
```

`hdmi_mixer.v` 第 6 行定义了这个参数（`parameter integer DEBUG_MODE = 0`），
第 89–144 行实现了 4 种模式：

| 值 | 屏幕上会看到什么 | 作用 |
|---|---|---|
| `0` | 正常摄像头画面 | 当前设置 |
| `1` | **8 条彩条**（红/绿/蓝/黄/青/品红/白/深灰，每条 128 像素） | **完全不依赖摄像头和 DDR**，只靠 HDMI 自己的时序 |
| `2` | 单色进度色块（黑→红→黄→绿→实时画面，出错显示蓝） | 看 `I_debug_status` 的阶梯值 |
| `3` | **4 格状态条**（每格 320 像素） | ⭐ **一屏看出摄像头链路卡在哪一步** |

**`DEBUG_MODE=3` 的 4 格含义**（代码 `design_top_wrapper.v` 第 472–480 行的注释 + 第 475–480 行的拼接顺序）：

从左到右：

| 格子 | 对应信号位 | 含义 | 亮起时颜色 / 未亮时颜色 |
|---|---|---|---|

### 5.2 如果连 `DEBUG_MODE=1` 的彩条都出不来

### 5.3 复位信号分析（为什么"纯白"意味着 PLL 大概率是锁定的）

从你工程的复位结构可以推出一条**很有用的逻辑**（以下三条均已逐行核实）：

`user_source\hdl_source\design_top_wrapper.v` 第 217–218 行：
```verilog
assign S_rst_n       = S_pll_lock;   // 第 217 行
assign S_hdmi_rst_n  = S_pll_lock;   // 第 218 行
```
同文件第 705 行：
```verilog
assign S_video_out_rst_n = S_hdmi_rst_n;
```

**即：三个复位全部由 PLL 锁定信号控制。**

推论：
- 如果 **PLL 没锁**（`S_pll_lock = 0`）→ HDMI 发送器一直被复位 → **根本没有 TMDS 输出** → 显示器只能显示"无信号"→ **B 类白屏**
- 所以你现在看到**纯白（A 类）**，反过来说明 **PLL 是锁上的、HDMI 发送器是活的**，
  问题就落在"送进 `hdmi_mixer` 的像素数据"上 → **请直接去做 5.1 的 `DEBUG_MODE=3`**

> **【已核实】** 上述三条复位连接来自 `design_top_wrapper.v` 的实际 `assign` 语句
> （第 217、218、705 行），并已逐行确认。

另外，`assign O_screen_pwm = 1'b1;` 位于同文件**第 213 行**（第 4 章 B3 条引用），
说明背光/PWM 这根线被**永久拉高、没有任何调光逻辑**。
