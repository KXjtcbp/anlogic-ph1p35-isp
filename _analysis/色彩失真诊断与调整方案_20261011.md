## 2. 色彩失真的定位

### 2.1 ★发现 A：采集链有色偏 + 对比度拉伸（截图不是 FPGA 的真实输出）★

**方法**：`anlogic_logo_rom.v` 是 FPGA 直接绘制的位图 OSD，每个覆盖像素存的都是精确 RGB 常量，`hdmi_mixer.v:1239-1242` 又是不透明覆盖、不混色。Logo 是左上角 160×160 的实心块，地址 = `局部y*160 + 局部x`。**于是 ROM 是画面上唯一的"已知输入色卡"**，把它和截图里同一坐标的像素比对，就得到采集链的传递函数。

**实测（脚本 `_analysis/scripts/_capture_chain_fit.py`，源图 `Screenshot 2026-10-11 17-00-21.png`）**：

| FPGA 写入（ROM/常量，已知） | 截图读到（实测） | identity 预测 | `(in−16)×255/219` 预测 |
|---|---|---|---|
| **(28, 45, 78)** ×3003 px | **(14, 33, 67)** | (28, 45, 78) ✗ | **(13, 33, 72)** ✓ |
| **(237, 28, 36)** ×785 px | **(251, 16, 24)** | (237, 28, 36) ✗ | **(255, 13, 23)** ✓ |
| (240, 28, 37) ×153 px | (253, 16, 24) | — | (255, 13, 24) ✓ |
| (238, 28, 36) ×132 px | (251, 16, 24) | — | (255, 13, 23) ✓ |
| `COLOR_DYN_TEXT` (255,242,0) OSD 黄字 | (255, 255, **9**) | (255,242,0) ✗ | **(255, 255, 0)** ✓ |
| `COLOR_ALG_TEXT` (0,255,136) MODE 绿字 | 只有混叠值，无纯常量 | — | (0, 255, 139) ✓ |

**只用"实心色块"（≥120 ROM 像素，即 logo 里没有被抖动的实心区）** 复核，结论更干净：

| FPGA 写入 | 截图读到 | `(in−16)×255/219` | 与 identity 的差 |
|---|---|---|---|
| (28, 45, 78) | (14, 33, 67) | (13, 33, **72**) | **(−14, −12, −11)** |
| (237, 28, 36) | (251, 16, 24) | (**255**, 13, 23) | **(+14, −12, −12)** |
| (240, 28, 37) | (253, 16, 24) | (**255**, 13, 24) | **(+13, −12, −13)** |
| (238, 28, 36) | (251, 16, 24) | (**255**, 13, 23) | **(+13, −12, −12)** |

⇒ 每个色块的 G、B 都**恰好掉 12 码**、R 都**恰好升 13~14 码**（因为 R 走 255 削顶）。这正是 `16→0` 黑位搬移加 `×1.1644` 增益的特征，而 identity 模型在每一道上都差 11~14 码。**结论无歧义。**

- 在 `17-00-21.png` 上：`pixels with R=255 & G=242 & B=0 : 0` —— **一个像素都不等于 FPGA 写的常量**。
- 散点图见 `_analysis/out/capture_chain_fit.png`（实心点 = 可信子集，淡点 = 抖动像素不可信）。
- 黄字笔画扫描线（y=198, x=645..750）呈 `ffff09 ffff15 ffff30 ffff3f ffff5e ffff63 ffff78 ffff7b ffff8b`：**R 与 G 恒被推到 0xff**，正是 `(242−16)×1.1644 = 263 → clip 255` 的结果。
- 结论：**采集卡输出的 16–235 limited range 被 OBS/采集软件当成 0–255 full range 解开了。**

**为什么这件事严重：**
1. 你所有的绝对色彩判断（以及 `tools/compare/compare.py` 报告里的 R/G、B/G、直方图）都隔着这一层。
2. 这个变换**在暗部会放大偏色**：两通道 20 vs 21（比值 0.952）→ (4×1.1644, 5×1.1644) = (4.7, 5.8)，比值掉到 **0.80**。所以"越暗越绿"有一部分是采集链制造的。
3. 它同时**拉伸对比度**（16→0、235→255），让画面在截图里显得比 FPGA 真实输出更"硬"、更"黑"。

### 2.2 ★发现 B：传感器侧完全没有白平衡，片上 AWB 是裸灰世界★

**传感器原生色（ChipWatcher 实测 RAW10，数字域、不受采集链影响）**：
```
test1.csv        R=79.95  G=93.37  B=81.72   -> 原生 R/G=0.8563  B/G=0.8753
室内常光2.csv     R=99.16  G=110.85 B=91.43   -> 原生 R/G=0.8946  B/G=0.8248
全黑.csv          R=66.37  G=67.94  B=66.07   -> 近黑，三通道自然接近 1.0
```
⇒ **室内光下传感器原生就偏绿：R/G ≈ 0.86~0.89、B/G ≈ 0.82~0.88。**

**传感器初始化表里没有任何白平衡寄存器**：
`proj/baseline/lab3/user_source/hdl_source/uics500_cfg/uics500reg_720p60.v` 的 `REG_SIZE = 9'd123`（索引 0..122）里只有曝光（索引 94/95/96 = `0x3e00/0x3e01/0x3e02`）、模拟增益（112/113、118/119 = `0x3e08/0x3e09`）、数字增益（121/122 = `0x3e06/0x3e07`）、测试图（116 = `0x4501`）。**没有 0x3e28/0x3e2a 之类的 WB gain，也没有 0x3c00 的 AWB 控制。**

**片上 `awb.v` 仿真证明它"能动"，但结构上是裸灰世界**（TB `_analysis/sim/awb/tb_awb_probe.v`，恒定 R=80/G=100/B=90）：
```
# --- end  : gainR=14000 gainB=11c71 donecnt=1536
#     expect gainR=0x14000 (1.250x)  gainB=0x11c71 (1.111x)
# *** gains moved ***
```
增益精确收敛到灰世界理论值 ⇒ 除法器和增益通路**没问题**。但：
- `awb.v:139-175` 累加器在 `I_tuser`（每帧，已用 TB 与源码双向确认 tuser 是**每帧**不是每行）上把和与增益一起清零；
- 增益**没有阻尼、没有时域平滑、没有死区**，上限 16×（`20'hfffff`）过松；
- 测量与施加在同一条码流上 ⇒ **永远追不上的移动靶**；
- 灰世界假设被"暖色木架 + 暖光"的室内场景误导（灰世界会把偏暖的场景压成偏绿）。

**残留偏色（把发现 A 的逆变换代回，得到 FPGA 域的真实比值）**：
```
17-00-12  png R/G=0.8789 B/G=0.9085  ->  fpga R/G=0.9162 B/G=0.9367
17-00-21  png R/G=0.9512 B/G=0.9811  ->  fpga R/G=0.9595 B/G=0.9843
17-00-30  png R/G=0.8598 B/G=0.9966  ->  fpga R/G=0.9109 B/G=0.9978
17-00-42  png R/G=0.9520 B/G=0.9797  ->  fpga R/G=0.9625 B/G=0.9841
17-01-49  png R/G=0.9635 B/G=0.9655  ->  fpga R/G=0.9751 B/G=0.9764   <- 绝对均匀灰，最可信
```
⇒ 中性目标上仍有 **约 2.5% 偏绿**（`17-01-49`），暗场景到 **8~9%**。

已排除的可能原因（**死路，不要重查**）：
- 除法器位宽截断（`divider` 48/32 位匹配，`uicfgcs500` 传的是真 Q16 商）；
- `done` 不脉冲 / `start` 电平不合法（**TB 实测 done 每行脉冲 64 次**）；
- `I_tuser` 是每行导致累加器每行清零（**TB + `demosaic.v:139` + `raw_matrix_3x3_buffer.v:394` 三处一致证明是每帧**）；
- 拜耳顺序错（RAW10 里 R≈B 且都低于 G，是"缺白平衡"的signature，不是 R/B 互换的 signature）；
- 采集链"加了绿"（发现 A 证明它只是范围展开，三通道同一曲线，不加色）。

### 2.3 ★发现 C：画面不稳定★

同一场景（MODE 0）、30 秒内四张：**Y 均值 39.46 → 88.79 → 30.67 → 64.85**，**R/G 0.869 → 0.951 → 0.862 → 0.952**。
⇒ 亮度和色相同时在 ±2.5× 范围内游走。CNT 连续证明这不是复位造成的。

原因链条：传感器自动曝光在剧烈游走（曝光已顶到硬件上限 `0x07C6 = 1990 = 2×VTS−10`）+ 裸灰世界 AWB 无阻尼地追 AE。

### 2.4 ★发现 D/E：黑位被抬起、暗部噪声被放大（"糊成一团"的直接原因）★

**黑位**（`mipi_to_raw_converter.v:44` + `isp_gamma.v` 内联表）：
```
盖镜头 raw10 实测均值 67  -  BLACK_LEVEL 56  =  11
11 + ROUND_ADD 2 = 13 ,  13 >> 2 = 3  (8bit)
gamma(p160_a050)[3] = 160*(3/160)^0.5 = 21.9 -> 22
```
⇒ **盖上镜头，画面上是 22 码的灰，不是黑。** 这正是"糊"的来源——黑位不下沉 + 低对比 = 一片发灰发绿的浆糊。

**噪声**：
```
17-00-21 最平坦 64x64 块 std = 3.704 码   (8bit)
17-00-42 最平坦 64x64 块 std = 3.802 码
17-00-12 最平坦 64x64 块 std = 4.034 码
```
曲线 p160_a050 的暗部斜率 `dy/dx = 80/sqrt(160x)`，在 x=10 处 = **2.0**，x=3 处 = **3.65**。
⇒ 传感器 1.5~2 码的暗部噪声被放大到 3~4 码（再被采集链 ×1.1644）——与实测 3.7~4.0 完全吻合。

已排除："糊"**不是**分辨率/聚焦问题（`crop_stack_1to1.png` 目视确认书的绿/蓝/棕等真实色彩还在，边缘结构可辨，只是被偏色 + 低对比 + 噪声淹没了）。

## 3. 调整方案

### 第 0 步（免费、必须最先做）：修正采集链的色彩范围

不改 FPGA，只改 OBS / 采集卡设置，让采集链变成恒等变换。

**目标**：让截图像素 = FPGA 输出像素。

**验收判据（自证式，不需要任何外部工具）**：重采一张，用
```powershell
& $py "E:\FPGA\_analysis\scripts\_capture_chain_fit.py"
```
必须满足
- Logo 区读到 **(28, 45, 78)**（主蓝底）和 **(237, 28, 36)**（红三角）；
- CNT 黄字区读到 **(255, 242, 0)**；
- 报错量 `identity` 模型的整体 RMS 应降到 **< 3 码**（现在 `limited->full` 是 22.9，identity 是 23.6，两个都大是因为采样按地址取点混入了相邻像素；**只有前两个大色块可信**）。

**改哪里**（按可能性排序）：
1. OBS → 来源 → 视频采集设备 → 属性 → **色彩范围 / Color Range**（把 Partial/Full 切换成另一个值）；有的采集卡在"配置视频"对话框里也有 `Range / Quantization` 选项。
2. OBS → 该来源 → **色彩空间 / Color Space**（Rec.709 ↔ Rec.601 与卡一致）。
3. 采集卡自带软件里把输出改成 **Full Range / RGB**。
4. 实在改不动：在 OBS 给该来源加一个 **LUT 滤镜**，反着来一遍（`in*219/255+16`）——不推荐，但能救。

> ★这一步不做，后面所有"颜色好不好"的判断都不可信★，包括我给你的一切色彩数字。

### 第 1 步（核心色彩修复）：加一个"阻尼 + 钳位 + 手动微调"的白平衡

**放在 FPGA 里做（不是传感器），既符合赛题"所有算法在 FPGA 中自主实现"，又是加分项素材。**

**关键洞察：WB 增益每个通道每帧只算一次，所以增益域里任何复杂运算几乎不要资源；真正贵的是每像素的三次乘法，而那个已经在 `awb.v` 里了。**

所以**不需要新增任何每像素乘法**，只改 `awb.v` 的增益来源。建议改成：

```verilog
// ---------------- 白平衡增益整形（每通道每帧一次，零像素级代价）----------------
localparam [19:0] WB_GAIN_MIN = 20'h08000;   // 0.500x
localparam [19:0] WB_GAIN_MAX = 20'h40000;   // 4.000x  (原来是 16x，过松)

// 手动微调寄存器（Q8 定点，256 = 1.000x），由参数寄存器/按键驱动
//   WB_R_TRIM / WB_B_TRIM：默认 8'd256
// 最终增益 = damping(divider 输出) * trim >> 8

reg [19:0] wb_r_damp [3:0];
reg [19:0] wb_b_damp [3:0];
integer c;
always @(posedge I_clk or negedge I_rst_n) begin
    if (!I_rst_n) begin
        for (c = 0; c < 4; c = c + 1) begin
            wb_r_damp[c] <= 20'h10000;
            wb_b_damp[c] <= 20'h10000;
        end
    end else begin
        for (c = 0; c < 4; c = c + 1) begin
            if (done[c]) begin
                // 钳位
                if (in_r_x[c] > WB_GAIN_MAX)      wb_r_tgt[c] = WB_GAIN_MAX;
                else if (in_r_x[c] < WB_GAIN_MIN) wb_r_tgt[c] = WB_GAIN_MIN;
                else                              wb_r_tgt[c] = in_r_x[c][19:0];
                // 一阶阻尼：g += (target - g) >>> WB_DAMP_SHIFT  (建议 3 ~ 5)
                wb_r_damp[c] <= wb_r_damp[c] + ((wb_r_tgt[c] - wb_r_damp[c]) >>> WB_DAMP_SHIFT);
                // B 通道同构
            end
        end
    end
end

// 手动微调（每通道每帧一次乘法，2 个 DSP 或移位加法即可）
wire [27:0] wb_r_eff = wb_r_damp[0] * {12'd0, WB_R_TRIM};   // >>8
```

同时把 `I_tuser` 上的**增益清零**删掉（只清 `sum_*`，不清增益），否则每帧开头几十拍用 1.0×。

**再叠一个"手动优先"挡位**，方便你在台上 5 分钟拨准：
```
WB_MODE = 0 : 自动（阻尼后的 AWB 增益）
WB_MODE = 1 : 手动（直接用 WB_R_GAIN / WB_B_GAIN 寄存器，跳过除法器）
WB_MODE = 2 : 自动 × 手动微调（推荐默认）
```
手动挡让整个系统**确定性**，不再随场景漂移——这一条就能解决"颜色一直变"。

**上板验收标准（摄影语言）**：
1. 对着白纸/灰卡：屏幕白纸应呈中性白，R/G 与 B/G 落在 **0.99~1.01**（用修正后的截图统计）。
2. 木架/皮肤不应发青。暖光源下画面整体偏暖是**正确**的（那是光源的色温，不是错误）。
3. 连续拍 5 张（间隔 5 s）R/G 的**标准差 < 0.01**（现在跨 0.86~0.95，标准差 0.05）。
4. 盖住镜头：RGB 三通道均值都 < 3 码。

### 第 2 步（色调修复）：黑位下沉 + 重新设计曲线

两个动作：

**(a) 黑电平参数**：`BLACK_LEVEL = 10'd56` 保留（实测 RAW10 基座 57~79，56 = 最小值−1，数学上不可能钳掉真实像素）。但要在曲线里把 `gamma[0..2]` 压到 0，**不要**用 `160*(x/160)^0.5` 这种把 2 映射到 18 的幂曲线。

**(b) 换曲线**：把 `_analysis/lut/gamma_lut_twoseg_p160_a050.hex` 换成带**趾部（toe）**的版本。推荐形式：

```
x <= T (趾部，压黑):           y = 255 * (T/255) * (x/T)^1.4     -> y(0)=0, y(1)=0
T < x <= P (中间调，微提):      y = 线性/幂函数连接
x > P (高光，压回):             y = ...                            -> y(255)=255
```

关键约束（用现有工具即可验证）：
- `y(0) = 0`、`y(1) = 0`、`y(2) = 0`  ⇒ 盖镜头就是纯黑
- `y(255) = 255`（不过曝不削顶）
- 暗部斜率 `dy/dx` 在 x=8 处 **≤ 1.2**（现在 p160_a050 是 2.24）⇒ 噪声不再被放大
- `y(128) ≈ 128 ± 6` ⇒ 中间调不漂

生成脚本沿用 `_analysis/scripts/gen_gamma_lut_twoseg.py` 的结构，输出后**必须**用 `_analysis/scripts/gen_blc_module_a.py` 的断言核对内联表与 hex 逐条一致（这是防"表全 0、上板全黑而报告全绿"的唯一手段）。

**(c) 可选：曲线强度用 SW2 三挡**，方便现场演示"关 / 弱 / 强"。

### 第 3 步（可选）：降噪

如果第 2 步后仍有可见颗粒：
- **最便宜**：在图曲线前做 3×3 中值（已有 `line_buffer_demosaic.v` 的行缓存可复用；或用 `my_algo.v` 里卡通化已有的 3×3 窗口）。
- **更便宜**：对 G 通道单独做一次 2 抽头平均（Bayer 的 G 是 R/B 的两倍采样率，降 G 的噪声最划算）。
- 资源上：`#eram 60/108`、`#slice 17874/21216 = 84.25%`、`#dsp 8/40`，`#slice` 余量只有 15.75%，**加 3×3 中值要小心**（估算 +800~1500 LUT）。建议先做前两步，再评估。
