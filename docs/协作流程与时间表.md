### 两条不可越过的线

1. **11-01 之后不再改 RTL。** 11-02 ~ 11-03 只允许改常量/参数（不新增逻辑、不改位宽、不改接口）。
   理由：任何 RTL 改动都要重新综合（约 16 分钟）+ 重新布线 + 重新上板回归。
   > 因为 QSPI 固化已移出关键路径（见第八节），这条线相比原方案已放宽 6 天；如果开发确实吃紧，可以再放宽到 **11-02**，代价是收尾只剩 1 天。
2. **本地未推送的改动不得超过 24 小时。**
   哪怕只跑通一个 TB、只写了一半，也 push 到自己的 `feat/*` 分支（`wip:` 开头的提交完全可以）。
   理由：① A 随时能看到进度，不用天天问；② 早暴露路径/版本/环境问题；③ 防止本地环境出意外。

## 三、提交节奏约定

三人同宿舍，用「当面催 + 群里一句话」代替固定例会。

| 角色 | 频率 | 内容 |
|---|---|---|
| B / C | **每天至少 push 一次**到自己分支 | 允许 `wip:` 开头的半成品提交 |
| B / C | 每有「一个可独立验证的单元」就开一个 PR | 不要憋大 PR |
| B / C | 每天群里一句话 | 今天推到哪个分支 / 卡在哪 / 明天要什么 |
| A | **不设固定集成窗口**，一攒够可验证的改动就集成 | 拉分支 → 综合 → 记 QoR → 上板 → 回贴 |
| A | 上板后 **24 小时内**回贴反馈 | 实拍图 + `stat_imgs.py` 输出的数字 |

> 不设固定窗口的理由：B/C 每天投入时间不固定，A 没必要按日历等。改成「**A 手上有空的比特流就烧**」，反而能提高集成次数。

## 四、分支 / PR 约定

```
main                 ← 只有 A 能推；受保护（评审模式）
feat/awb-robust      ← B
feat/gamma-scurve    ← C
feat/ae              ← A（专项任务）
```

- B/C **不要直接推 `main`**。
- 触碰 `design_top_wrapper.v`（三人冲突热点）时，`commit message` **首行必须写** `TOUCHES: design_top_wrapper.v`。
- PR 描述必须回答五个问题（见 `docs/团队协作指南.md` §6）：
  改了哪些文件的哪些行 / 每处目的 / 烧录后应该看到什么（摄影语言 + 可测数字）/ 哪些地方不应该变 / 哪里没验证。

### commit message 格式

```
<type>(<scope>): <一句话>

TOUCHES: <冲突热点文件，可选>
- 现象：...
- 改法：...
- 验证：TB ALL PASS errors=0；compile_check 39/40
```

`type`：`feat` / `fix` / `docs` / `chore` / `refactor` / `wip`

## 六、每次交付前必跑（B/C 自查清单）

```bash
# 1) 语法检查：必须 39/40，唯一允许失败的是 ddr_wrapper 的 dhi_clk
python <REPO>/_analysis/scripts/compile_check.py

# 2) 你自己的 Testbench：必须 ALL PASS, errors=0
#    （命令见 docs/团队协作指南.md §5.2）

# 3) 确认没有引入乘法器（会让你新增 DSP）
grep -nE "[a-zA-Z0-9_\]\)]\s*\*\s*[a-zA-Z0-9_\(]" <你改的文件>
#    这条会误报注释和位宽声明，人工过一遍即可；重点是别写 a*b

# 4) 确认没有碰禁区
git diff --name-only main | grep -E "mipi_to_raw_converter.v"
git diff main -- proj/baseline/lab3/user_source/hdl_source/design_top_wrapper.v | grep -nE "S_blk_bypass"
```

## 八、QSPI 固化（暂缓，移到线下阶段）

**赛题原文要求**：「最终提交设计必须固化在开发板上、上电即可运行、无需再使用 PC 下载。」

**当前决定：暂缓。** 理由：

1. 它是全项目唯一「完全没验证过」的流程，风险最高，但**与图像算法完全解耦** —— 固化只是把已生成的 `.bit`
   写进板载 QSPI Flash，不影响 RTL 内容。所以它**不占用开发期**。
2. 11-04 之前的每一小时都应该留给开发（AE、AWB、曲线三条线都还没收敛）。
3. 后续进入线下阶段时再专门打通，届时每次新的 `.bit` 都可以复用同一套流程。

**风险与对策**：如果线下阶段才发现固化流程走不通，会很难补救。因此**在 11-02~11-03 的收尾期内，
至少要留出半天做一次「只读性质的调研」** —— 把 `官方资料/` 里的开发板手册、`anlogic_example/` 的例程、
TD `Tools → Programmer` 的 QSPI 选项摸清楚，写成一页操作卡，但不实际烧。真正烧写留到线下。

**动手前的准备清单**（线下阶段开工时用）：

- [ ] 读 `官方资料/` 里的开发板手册（QSPI 编程章节）
- [ ] 确认 TD Programmer 里选哪个模式（External Flash / QSPI）、文件要用 `.bit` 还是别的格式
- [ ] 确认板载 QSPI Flash 容量与型号（手册记录为 128 MB）
- [ ] 确认 AL-LINK-FT 下载器在「不接 PC」时是否还需要跳线/拨码
- [ ] 确认固化后如何回退（还能不能重新用 JTAG 覆盖）
- [ ] 写一页《QSPI 固化操作卡》放进 `docs/`
