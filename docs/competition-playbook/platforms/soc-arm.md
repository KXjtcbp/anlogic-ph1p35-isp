# 平台卡 · SoC + ARM（带操作系统）

> **内容来源标注**：本卡是 `[外部]`（通用嵌入式 Linux / RTOS 工程实践），**不是本次实践的亲验结果**。
> 覆盖：Zynq（ARM + FPGA）、RK3568/RK3588、i.MX、全志、树莓派、Jetson 等。

---

## 0. 一句话定位

**最强：既能算（CPU/GPU/NPU）又能连（网络/显示/存储），且有成熟驱动与生态。**
**最不适合：硬实时**（Linux 下调度抖动毫秒级）、**极低功耗常开**。

---

## 1. 能力清单

| 层 | 典型配置 |
|---|---|
| ① 感知 | USB 摄像头、MIPI CSI、GPIO、I2C/SPI/UART 传感器、音频输入 |
| ② 执行 | GPIO、PWM、继电器、步进/伺服（经驱动板）、HDMI/DSI 显示、音频输出 |
| ③ 算力 | 多核 ARM + 可选 GPU/NPU（Jetson 有 CUDA；RK 有 RKNN） |
| ④ 通信 | 以太网、WiFi、BLE、4G、USB、CAN |
| ⑤ 呈现 | HDMI/LCD、网页（本地起服务）、手机 App、云平台 |

> **Zynq 类特殊**：ARM 与 FPGA 在同一芯片内，**PS（ARM）与 PL（FPGA）之间可以走 AXI 总线**。这是"既要并行又要操作系统"的唯一舒服方案，但学习曲线最陡。

---

## 2. 资源口径

| 项 | 注意 |
|---|---|
| 内存 | GB 级，通常不是瓶颈；但**内存带宽**常是瓶颈（摄像头 + 显示 + 推理同时跑） |
| 存储 | eMMC / SD 卡；注意**写寿命**（日志和临时文件不要一直写 SD） |
| NPU/GPU | 标称 TOPS 是理论值；实际受量化、算子支持、内存带宽限制，**通常打三到五折** |
| 实时性 | Linux 非实时内核调度抖动 ms 级；要 µs 级需 `PREEMPT_RT` 或把关键环放到 MCU/FPGA |

## 3. 工具链与最小验证路径

| 环节 | 典型做法 | 关键检查 |
|---|---|---|
| 系统镜像 | 厂商提供的镜像 / Yocto / Buildroot | **先烧官方镜像跑通，再改** |
| 交叉编译 | `aarch64-linux-gnu-gcc` + CMake | 确认 `file` 看架构对不对 |
| 部署 | scp / NFS / U 盘 / OTA | 改完的二进制**版本号要能打印出来** |
| 最小验证 | 摄像头出图 / 一个 Python 脚本读传感器 + 打印 | 通了再上算法 |
| 调试 | ssh + `dmesg` + `top` + `perf` + 串口控制台 | **串口控制台一定要接**（系统起不来时只有它能救） |

- **★什么算"构建成功"★**：镜像能启动到登录 **且** 串口控制台可用 **且** 目标程序能跑并打印版本号。
- **冷启动**：断电再上电（不是 `reboot`），验证真的能自启。

## 4. 这类平台的专属坑

| 坑 | 表现 | 怎么避 |
|---|---|---|
| 系统起不来 | 黑屏、ssh 连不上 | **永远接串口控制台**，看 kernel log |
| 驱动不匹配 | 摄像头/显示屏换了型号就不工作 | 先用厂商镜像验证硬件，再改软件 |
| 电源不足 | 大负载时重启 / 摄像头掉线 | 用带独立供电的 Hub；看电压跌落 |
| SD 卡写坏 | 跑几天后系统崩 | 只读根文件系统 / 日志写内存 / 换 eMMC |
| 依赖地狱 | 换台机器就编不过 | 用 Docker 固化编译环境 |
| 库版本冲突 | 同一个包两个版本 | 虚拟环境 / 容器 |
| 时序抖动 | 控制环偶尔超时 | 关键环放 MCU/FPGA；或 `PREEMPT_RT` + CPU 亲和性 |
| 散热 | 跑一会儿降频 | 加散热片/风扇；看 `thermal_zone` |
| 自启没配 | 手动能跑，断电重启不会跑 | 用 systemd service，**断电测一次** |

## 5. 交付物检查项

- [ ] 完整源码 + 编译脚本（Dockerfile / CMakeLists / Makefile）
- [ ] **系统镜像或烧录说明**（评委要能复现）
- [ ] 依赖清单（`requirements.txt` / `package.json` / `apt list`）
- [ ] 模型权重文件（如果用了 AI）+ 量化说明
- [ ] 自启配置（systemd service 等）
- [ ] 关键指标：分辨率/帧率/推理耗时/CPU 占用/温度
- [ ] `README_CODE.txt`：哪几部分是自研、哪几部分是开源移植、改了哪里

> **`[推断]` 这类平台最容易被评委追问"这是你写的还是调库"**——所以 `README_CODE.txt` 里"哪些是自研、哪些是移植、移植改了什么"必须写清。

## 6. 判据怎么写

| 目标 | 可测判据 |
|---|---|
| 通路打通 | 摄像头出图帧率稳定在 X fps，连续 10 分钟不掉 |
| 推理性能 | 单帧推理 < X ms，端到端 < X ms（用时间戳打点，不靠肉眼） |
| 资源占用 | CPU < X%、内存 < X MB、温度 < X °C |
| 实时性 | 控制环周期抖动 < X ms |
| 自启 | 断电 5 秒后再上电，X 秒内自动开始工作 |
| 长跑 | 连续 24 小时不崩、不泄漏（看内存曲线） |

---

## 7. 迁移提示

1. **"能跑 Python"不等于"能实时"**：Python + OpenCV 的帧率可能只有 5 fps。
2. **先烧官方镜像**，确认硬件没坏，再动自己的系统。
3. **串口控制台是救命线**，一定要接出来。
4. **自启要断电测**，不是 `reboot` 测。
5. **开机时间是硬伤**：Linux 从通电到能用可能十几秒，如果比赛要求"上电即工作"，要提前评估。
