# 06 · 复盘与迭代机制

> 复盘不是为了自我安慰，是为了**让下一场比赛从更高的起点开始**。
> 这一份解决一个问题：**赛后做什么，才能让上面五份文件越用越准。**

---

## 1. 赛后 48 小时内（趁记忆还热）

不要等"缓过来再说"。48 小时后细节就模糊了。

### 1.1 先归档，再思考

- [ ] 把最终提交的所有文件 + 每个文件的 md5 记进 `docs/提交存档.md`
- [ ] 把**最终交付的比特流/固件/工程包**单独存一份，标注"已提交版本"
- [ ] 把演示视频、报告、海报各复制一份到 `docs/submitted/`
- [ ] 把最后一个月的工作区**整体打一个包**（不用整理，原样存）

> 理由：半年后你想复现"当时到底是哪个版本"，只有这堆东西能回答。

### 1.2 立刻写"三件真事"

不用写完整报告，先写三个句子：

1. **这次做出来的、最得意的一个东西是什么？**（一句话）
2. **这次最痛的一个教训是什么？**（必须带具体数字或具体场景，不能写"经验不足"）
3. **如果只能改一件事重来，改哪件？**

> 这三句是后面所有复盘的种子。写不出来说明还没想清楚。

---

## 2. 复盘清单模板（一周内写完）

分五部分，每部分不要长，但要**具体到可执行**。

### 第一部分 · 经验（按"如果重来我会怎么做"写）

| # | 当时的做法 | 结果 | 如果重来 |
|---|---|---|---|
| 1 | | | |

**要求**：每条必须能对应到上面五份文件里的某一节。对不上的，说明这条经验还没沉淀，要补进去。

### 第二部分 · 我学到了什么

分成两类写，不要混：

- **能独立做的**（下次可以自己来）：写下具体动作，比如"能独立跑完 改→编译→上板→看变化 的闭环"
- **能识别好坏的**（判断力）：写下具体判据，比如"能看出构建报告里的数字是不是真的变了"

> **判断力的进步比技能的进步更值钱**，但更难被自己察觉。刻意写下来。

### 第三部分 · 能力提升表

| 能力 | 赛前 | 现在 | 依据（具体事件） |
|---|---|---|---|
| | | | |

**要求**：「依据」一栏不能空，也不能写"感觉进步了"。要写可指认的事。

### 第四部分 · 待补能力（按优先级）

- **P0**：下次比赛前必须补的（不说清楚就会重蹈覆辙的）
- **P1**：下次比赛前最好补的
- **P2**：可以边比赛边学的

**要求**：P0 不超过 3 条。超过 3 条等于没优先级。

### 第五部分 · 可进步方向

按五个维度各写一条：

| 维度 | 下次具体怎么做 |
|---|---|
| 方法（流程、判据） | |
| 思路（选题、架构） | |
| 工具（工具链、脚本） | |
| 协作（分工、集成） | |
| 表达（报告、演示、答辩） | |

## 3. 怎么更新这套 skill（关键）

**这是本文件存在的唯一理由。** 下次比赛后，按下面的规则改，而不是"想起来就改一点"。

### 3.1 更新触发条件

| 发生了什么 | 改哪个文件 | 怎么改 |
|---|---|---|
| 踩了一个**上面五份里没写**的坑 | `05-避坑清单.md` | 加到对应阶段，标注 `[实践]`，写清「坑/表现/怎么避」 |
| 某个判据**设错了**（太松或太严） | `03` §3 判据表 | 改那一行的数值，并在旁边注明"原值 X，因为 Y 改成 Z" |
| 发现**新的假成功形态** | `03` §5 四判据 | 加一个案例（现象 / 根因 / 怎么提前发现） |
| 找到**更好的选题方法** | `02` | 加在四种方法之后；如果它比四问法更好，替换四问法并说明理由 |
| 投入比例**明显偏离** | `01` §2 表 | 更新"实际"那一列，并在下面写一句偏差原因 |
| 换了一个**同类竞赛** | `_本项目配置.md` | 只改配置，方法文件不动 |
| 竞赛规则/提交要求**变了** | `_本项目配置.md` §5 | 更新提交项清单与限制 |

### 3.2 更新的三条纪律

1. **只加验证过的**。没验证的一律标 `[外部]` 或 `[推断]`，不标 `[实践]`。
2. **改旧条目要留痕**。不要悄悄改数字，写成"原值 X → 新值 Y，因为 Z"。否则下次你不知道为什么是这个数。
3. **一次复盘只改 3~5 处**。改太多说明没想清楚，或者把整份文件重写了一遍（那等于没积累）。

### 3.3 版本管理

```bash
# 每次比赛结束后，给它打一个标记
git tag playbook/<竞赛名>-<年份>
git commit -m "playbook: 根据 <竞赛名> <年份> 复盘更新 <改了哪几节>"
```

> 理由：下次你能 diff 出"上一次我加的是什么、这一次改的是什么"，这本身就是一种复盘。

## 4. 下一次比赛启动时怎么用

1. 新建工作区，把 `competition-playbook/` 整个目录复制进去
2. 填 `_本项目配置.md`（10 分钟）
3. 新开一个对话，粘贴 `README.md` §3 里的四行提示语
4. 从 `02-题目到方向.md` 的四问法开始

> **如果配置填不完，说明你对这场比赛的了解还不够**——那比选错技术方向更早暴露问题。

## 5. 关于"没进决赛"这类结果

### 5.1 判断"输在哪"要看权重，不要看情绪

一个可用的权重拆法（**`[推断]` 基于本次经验，不是官方口径**）：

| 因素 | 大致权重 | 怎么验证 |
|---|---|---|
| 选题方向（有没有"要解决的问题"） | 40% | 把报告里的"应用"章节删掉，作品变不成立吗？ |
| 关键技术选型（自研 vs 用现成） | 25% | 你的功能和别人比，是"更少但更深"还是"更少且更浅"？ |
| 信息差（知不知道要比什么） | 20% | 能不能说出 3 个往届获奖作品做了什么？ |
| 竞争强度（今年卷不卷） | 15% | 这个你控制不了 |

**要求**：先把这个表填一遍（换成你自己的判断和依据），再决定"下次改什么"。
**不要**把结果归因到"今年太卷"——那一条只占 15%，且你控制不了。

### 5.2 复盘要避免的三种写法

- **空泛自省**：「经验不足」「准备不充分」「团队配合有待加强」——这三句可以套在任何一场比赛上，等于没写
- **只写技术**：技术只是执行层。选题、判断、材料，往往比技术更影响结果
- **只写成功**：没有失败记录的复盘，下次会重复同样的失败

### 5.3 一个有用的自检

> **如果明年有一个和你水平差不多的人，拿着你现在这套东西去打同一场比赛，他会比你打得好还是差？**
>
> 如果答案是"差不多"——说明你没沉淀出东西。
> 如果答案是"明显好"——说明这套文件真的有用。

## 6. 一句话

> **比赛只打一次，复盘打一辈子。**
> 每一次比赛的真正产出不是那个作品，是**你下次能少走的那几步路。**
