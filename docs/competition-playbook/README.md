# 工科竞赛通用方法论 · Playbook

> 一套与具体赛题解耦的竞赛打法。来源 = 2026 年全国大学生嵌入式芯片与系统设计竞赛 FPGA 创新设计赛道（选题二，安路 PH1P35）的完整参赛实践 + 同类竞赛（集创赛 / 电赛 / 智能车）公开的获奖经验。

---

## 0. 这份文档是什么

不是教程，是**一份在比赛的每个阶段都能来查的作战手册**。它回答三个问题：

1. **现在这个阶段，我该把时间花在哪？**（→ `01`）
2. **题目看不懂 / 不知道能干什么，怎么往下推？**（→ `02`）
3. **东西做出来了，怎么判断它是真的能用？**（→ `03`、`04`）

---

## 1. 适用场景与触发条件

**在以下任一情况出现时，应读取并使用本 skill：**

| 触发条件 | 该读哪份 |
|---|---|
| 刚报名 / 刚拿到赛题，要定方向 | `02-题目到方向.md` |
| 要排时间表、决定每阶段投多少 | `01-流程与投入重点.md` |
| 开始建工程 / 选架构 / 算资源 | `03-工程搭建与调试.md` §1–§2 |
| 改了东西但"看不出有没有效果" | `03-工程搭建与调试.md` §3–§4 |
| 怀疑构建是"假成功" | `03-工程搭建与调试.md` §5 |
| 提交前 3 天 | `04-提交前核查与打包.md` |
| 踩了坑想记录 / 想避免重复踩 | `05-避坑清单.md` |
| 比赛结束 | `06-复盘与迭代.md` |

**不适用**：课程作业、课程设计、纯软件项目（可以借 `01` 和 `04`，但 `03` 的工具链部分不适用）。

## 2. 标注约定（全文通用）

文档里每条经验都带来源标记，**读的时候请注意区分可信度**：

- **`[实践]`** —— 本次比赛亲身验证过，有具体数字或可复现步骤。
- **`[外部]`** —— 来自同类竞赛公开作品/复盘、开源项目、教材，**未在我们自己手上验证**，采纳前请自行判断。
- **`[推断]`** —— 基于现有证据的合理推测，不是实测结论。看到这个标记，决策前要自己补验证。

> 混用这三种来源是写复盘最常见的错误：把"我觉得"写成"实践证明"，下一次就会照着错的做。

## 3. 在新对话中如何引用这份文档

**推荐做法**：每次开新对话，把下面这段原样贴进第一条消息。

```
先读这三份文件，再回答我：
1. E:\FPGA\docs\competition-playbook\README.md
2. E:\FPGA\docs\competition-playbook\_本项目配置.md
3. 按 README 第 1 节的触发条件表，读当前阶段对应的那一份

读完后：
- 用 3 句话概括当前阶段我该做什么、不该做什么
- 指出我这次比赛配置里缺了哪些字段（_本项目配置.md 里的「待填」）
- 然后开始干活
```

**为什么读两份而不是一份**：
- `README.md` 是方法（对所有比赛都一样）
- `_本项目配置.md` 是这次比赛的参数（赛题名、芯片、工具链、评分表路径、提交项）
- 把"方法"和"参数"分开，方法就不会被某一次比赛的具体细节污染

**如果换了比赛**：复制整个 `competition-playbook\` 文件夹到新工作区，只改 `_本项目配置.md`。

## 5. 一句话总纲

> **选题和方案阶段改主意是免费的，实现阶段改主意是很贵的，提交前改主意是不可能的。**
> 所以时间要倒过来投：越是前面，越要多花。
>
> 我们这次的失分，80% 在选题那一周就决定了。
