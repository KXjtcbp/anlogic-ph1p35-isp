# 04 · 提交前的核查与打包清单

> 提交阶段的错误**不可逆**。这一份必须逐项打勾，不要凭记忆。

## 1. 先列清单：把"要交什么"写成表

打开赛题/通知，把每一个提交项抄成一行。**只写文件名的清单不叫清单。**

| # | 提交项 | 格式要求 | 大小限制 | 平台 | 状态 |
|---|---|---|---|---|---|
| 1 | 全部代码 | 压缩包（RAR/ZIP） | ≤ 200 MB | 表单上传 | ☐ |

> **`[实践]`** 上面的限制（200 MB / 50 MB / 3 个关键词）是从我们那次的提交表单截图里抄下来的。**每次比赛都要重新抄一遍，不要套用上一次的。**

## 2. 代码包：怎么组、怎么打

### 2.1 不要在原始工作区直接压

**`[实践]` 反例**：直接在 8 GB 的工作区上 `rar a`，会打进去：
- 厂商资料（几个 GB）
- 每次上板的采集图（一个 GB 级）
- 分析产物、日志、仿真中间文件（几百 MB）
- 已经打包过的旧压缩包

结果超过大小限制，或者压出一个没人看得懂的目录树。

### 2.2 标准做法：先建"干净目录"，再压

```powershell
# 1) 建一个空目录
$stage = "<工作区>\_submission\stage"
if (Test-Path $stage) { Remove-Item $stage -Recurse -Force }
New-Item -ItemType Directory -Path $stage -Force | Out-Null

# 2) 只复制需要的东西（用绝对路径写排除项）
robocopy "<工作区>\proj\<工程>\user_source" "$stage\code\user_source" /E /XD "<工作区>\_backup" "<工作区>\captures" /NFL /NDL /NJH /NJS
robocopy "<工作区>\proj\<工程>\td_project"   "$stage\code\td_project"   /E /XF *.log /NFL /NDL /NJH /NJS
robocopy "<工作区>\_analysis\scripts"        "$stage\analysis\scripts"  /E /NFL /NDL /NJH /NJS

# 3) 写一份 README_CODE.txt（说明目录用途、构建步骤、哪些是自研）
# 4) 打包
& "<RAR 路径>\Rar.exe" a -r -m3 -s "$stage\..\<包名>.rar" "$stage\*"
```

> **`[实践]` 坑 1**：`robocopy` 的 `/XD` `/XF` **必须写绝对路径**，写相对路径排除不掉。
> **`[实践]` 坑 2**：`rar a` 用 `-ep1`（剥掉一层目录）很容易把顶层结构搞乱，**先建好 stage 目录再对 stage 打包**最稳。
> **`[实践]` 坑 3**：`7z` **不能创建 RAR**（只能解）。要出 RAR 必须用 WinRAR 的 `Rar.exe`。

### 2.3 代码包里必须有什么（这一节最容易漏）

**必须有的：**

- [ ] 全部 `.v` / `.sv` / `.vh` 源文件（含 Testbench）
- [ ] **工程描述文件**（工具的那种 `.al` / `.prj` / `.qsf`）
- [ ] **约束文件**（时序 `.sdc` / 引脚 `.adc` / `.xdc` / `.lpf`），**所有子目录下的都要**
- [ ] **IP 的描述文件**（`.xml` / `.ipc` / `.tcl`），没有这些别人打不开你的 IP
- [ ] 生成脚本（LUT 生成、表拟合）——这是"你怎么做的"的证据
- [ ] `README_CODE.txt`：目录说明 + 构建步骤 + **哪几个模块是自研的**

**容易漏、但漏了会被扣大分的：**

- [ ] **时序报告**（`route.qor` / `.timing` / `timing_summary.rpt`）
- [ ] **面积报告**（`*.area`）
- [ ] **交付比特流**（`.bit` / `.sof` / `.bin`）
- [ ] 引脚分配表
- [ ] 资源/时序台账（一张 CSV 也行）

> **`[实践]` 我们漏了什么**：只保留了"代码"，把 `route.qor` / `phy.area` / `.bit` 全被扩展名过滤器剔掉了。
> `.al` 里引用的 61 个文件 61/61 都在——**代码一点不缺**，缺的是**证明它能跑的三个文件**。
> **代码不全只是形式，证明不了它能跑才是实质。**

### 2.4 `README_CODE.txt` 模板

```
<作品名> · <竞赛名> <赛道/题号>
提交日期：<YYYY-MM-DD>

一、目录结构
  code\            源码与工程（可直接导入 <工具名> <版本号>）
    <工程>\        <工具> 工程，顶层文件 <顶层文件名>.v
    <IP目录>\      第三方/官方 IP
  analysis\        分析脚本（Python 3，依赖 <依赖列表>）
  docs\            报告、框图、说明
  releases\        每个可上板版本的比特流与时序/面积报告

二、怎么构建
  1) <工具> 打开 <工程文件>
  2) 综合 → 布局布线 → 生成比特流
  3) 预期结果：Setup WNS ≥ <数值> ps，TIS = 0，
                #slices ≈ <数值> / <总数>，#RAMs ≈ <数值>，#DSPs ≈ <数值>

三、哪些是我们自己写的
  <逐个列出模块名 + 一句话作用 + 实测 LUT 占用>
  其余为官方 IP（<列出>），未做修改（或：修改点见 <文件>:<行号>）

四、怎么复现报告里的数字
  <脚本路径> --<参数>  （输入：<图片目录>；输出：<报告文件>）
```

> **为什么要专门写第三节**：评审很容易把"官方 IP + 自研模块"整体当成"抄的"。
> **一句话说明"这 8 个模块是我写的、各占多少 LUT"，就能把这个问题彻底关掉。**

## 3. 提交前的逐项打勾表

### 3.1 代码包

- [ ] 在**干净目录**重建，不在原始工作区压
- [ ] 记录压缩包的 **md5**（不是只看大小）
- [ ] 解压到另一个空目录，**试一次能不能打开工程**
- [ ] 抽查 3 个关键文件确实在包里（工程文件 / 约束 / 顶层 RTL）
- [ ] `README_CODE.txt` 里的构建步骤，你自己照着走一遍能通
- [ ] 包里**没有**：`_backup`、`captures`、中间产物、旧压缩包、含密钥的文件

### 3.2 视频

- [ ] 时长符合要求（没有要求就控制在 3 分钟内）
- [ ] 分辨率与画面清晰（做文字标注，别只放 BGM）
- [ ] **每一段功能都能在代码包里找到对应实现**
- [ ] 没有剪辑拼接造成的"功能拼凑"错觉（一块板、一个版本、一口气演示完）
- [ ] 片头有作品名、片尾有关键指标
- [ ] 上传后**自己下载回来播一遍**

### 3.3 报告

- [ ] 页数/格式符合要求（字体、行距、页边距）
- [ ] 数字与代码包、视频、海报**三处一致**（资源数、版本号、指标）
- [ ] 每张图都有图注，每个表都有表头
- [ ] 实物照片齐全（整机、接口特写、拨码状态）
- [ ] 导出 PDF 后**逐页看一遍**（字体替换、图被裁、表格断页）

### 3.4 GitHub / 仓库

- [ ] 仓库是 **public**（私有仓库评审点开就是 404）
- [ ] 首页 README 有：一句话说明、数据通路图、快速开始、模块表
- [ ] `.gitignore` 排除了大文件与中间产物
- [ ] 单文件 < 平台上限（常见 50 MB / 100 MB）
- [ ] 仓库总大小在平台软上限内
- [ ] 从**别人的电脑/无痕窗口**打开一次能看

### 3.5 关键词 / 一句话简介

- [ ] 3 个关键词**互不重复**，且每个都能在作品里指到具体东西
- [ ] 不要用"创新""高效""智能"这类空词
- [ ] 一句话简介能过"三分钟测试"（见 `02` §6）

### 3.6 最后 2 小时

- [ ] 所有文件已上传，**不是只放在本地**
- [ ] 表单每一项都填了，没有空着必填项
- [ ] 截图保存"提交成功"页面
- [ ] **提前至少 1 小时提交**

## 5. 一句话

> **提交阶段的唯一目标不是"做得更好"，是"别漏"。**
> 做得再好，漏一个文件就是零分；做得一般，材料齐全至少能拿到该拿的分。
