# 03 · 工程搭建与调试方法论

> 这一份是全文最值钱的部分：**怎么判断你做出来的东西是真的能用**。
> 如果你只读一份，读这份。

---

## 1. 工程骨架的搭建

### 1.1 从官方示例二次开发，不要从零写

**`[实践]`** 官方示例工程（`<官方例程名>`）已经把最难的、最容易出不来图的通路做好了：高速接口、时钟、缓存控制器、显示输出。从零写这些，两个月都不一定出图。

**正确做法**：
1. 先把官方例程**原样跑通**（能出图、能显示），记下它的资源占用和时序余量
2. 存档一份「原厂基线」（`.bit` + `route.qor` + `phy.area`），它是你后面所有问题的对照组
3. 在它上面**一次加一个模块**，每加一个就跑一次构建、上一次板

**`[实践]` 反例**：先写了 5 个模块再一起上板，结果出不来图，得一个一个回退找。

### 1.2 目录结构约定

```
<工作区>\
  proj\
    baseline\<官方例程名>\        ← 主战场，改动都在这里
    releases\                     ← 每个"可上板"版本一个目录
      2026-01-01_<里程碑名>\
        <工程名>.bit              ← 交付比特流
        <工程名>_compress.bit
        route.qor                 ← 时序与资源快照
        camera_to_dsi_display_phy.area  ← 面积报告
        readMe.txt                ← 这一版改了什么、md5、回滚方法
  _analysis\
    scripts\                      ← 所有自动化脚本（统计、拟合、打包、补丁）
    out\                          ← 分析产物（图、日志、报告），不入 git
    sim\                          ← Testbench 与仿真工程
  captures\                       ← 每次上板采集的图/视频，按日期+批次分目录
  docs\                           ← 交付文档
```

**为什么 releases 要这样放**：`[实践]` 我们最后有 34 个版本目录。每次出问题先烧一个"已知良好"的版本确认硬件没坏——**没有版本账，你会在半夜怀疑是板子坏了**。

### 1.3 每个版本必须记 4 件事

- 改了哪些文件（`git log --oneline` 够用）
- QoR：`Setup WNS` / `Hold WNS` / `#slices` / `#eriram` / `#DSPs`
- 比特流 **md5**
- 回滚方法（烧哪个版本）

> **`[实践]` 坑**：所有 `.bit` 的字节数往往**完全相同**（同一型号芯片的比特流长度是固定的）。
> 所以「文件大小对」**不能**证明「版本对」，**必须比 md5**。

## 2. 架构与资源

### 2.1 先算资源，再定架构

动手前先建一张表：

| 项目 | 预算 | 用什么换 | 余量 |
|---|---|---|---|
| LUT | ? | | ≥20% |
| 寄存器 | ? | | ≥20% |
| 片上 RAM | ? | | ≥20% |
| DSP | ? | | ≥30% |
| 时序余量 | ? ns | | 正数 |

> **`[实践]` 口径陷阱**：厂商标称的「<N> 个等效 LUT」和工具报告里的 `#lut6` 总量是**两个不同的数**（我们的芯片标称 38184 等效 LUT，工具里 `#lut6` 总数只有 21216）。**看百分比时只能用工具报告的分母。**

### 2.2 资源投向比资源效率更重要

**`[实践]`** 我们最后一次统计：自研逻辑约 8455 LUT，占整机 LUT6 的 51.6%；剩下 48.4% 是官方 IP 底座（高速接口、缓存控制器、显示输出）。

**结论不是"效率低"，是"投向分散"**：
- 8455 LUT 分散在 8 个小功能上（平均 1000 LUT/个）
- 每个都是"看不见的画质改善"或"粗糙的块级统计"
- 别人的 8000 LUT 只做 2~3 个点，但每个都**一眼能懂**

> **建议**：资源预算里**明确留 20% 给"评委看得见的东西"**（应用闭环、交互、视觉呈现），不要全花在链路优化上。

### 2.3 帧式 vs 全流水（最根本的架构分歧）`[外部]`

| | 全流水 | 帧式 |
|---|---|---|
| 延迟 | 固定几十拍（低） | 至少一帧（高） |
| 资源 | 高（要多份并行硬件） | 低（一份硬件反复用） |
| 实现难度 | 高（时序难收敛） | 中（有整帧时间可用） |
| 适合 | 强调"零延迟"的作品 | 强调"算法复杂"的作品 |

**`[实践]` 我们选了全流水**（延迟固定在流水线级数），这对"低延迟、实时"是加分；但代价是资源贵，同样的算法别人能用帧式省一半。

**建议**：赛题强调延迟就全流水，强调算法就帧式，**两者可以混**（关键路径全流水，重算法走帧式）。

### 2.4 哪些自己写、哪些用现成

| 类别 | 建议 | 理由 |
|---|---|---|
| 高速接口 / 时钟 / 缓存控制器 / 显示输出 | **用官方 IP** | 自己写不出来，且不是评分点 |
| 核心算法链路 | **自己写** | 这是"你能做什么"的证据 |
| 应用层算法（分类/检测/跟踪） | **可以移植开源，但要改接口并讲清每处改动** | 见 `02` §5 |
| 调试辅助（遥测、测试图） | **自己写，但别舍不得删** | 交版前要能关掉 |

## 3. 判据设定（本文件最重要的一节）

### 3.1 核心原则：先写判据，再动手

**动手改任何东西之前，先写下来："改完之后，什么数字变成什么，就算成功。"**

判据必须包含**三要素**：

1. **数值**——一个具体的数或区间（不是"更好看"）
2. **条件**——在什么场景下测（同机位？盖住镜头？白纸满帧？）
3. **复查方式**——怎么测（用什么工具、统计什么、看几个样本）

### 3.2 判据示例（可直接改用）

| 功能 | 判据 | 条件 | 复查方式 |
|---|---|---|---|
| 白平衡 | 整帧 R/G、B/G ∈ **0.98~1.02** | 中性白纸铺满画面、光照稳定 | 遮掉 OSD 后算全帧通道均值 |
| 暗角校正 | 逐列 R/G 的**极差下降 ≥50%** | 同机位、同光照、只拨一个开关 | 逐列统计通道比，取 max−min |
| 自动曝光 | 帧均值落在目标 **±5%**，且不触发高光保护 | 同一场景连拍 10 张 | 统计帧均值与过曝像素占比 |
| 运动检测 | 静止时**零误检**；目标出现**1 秒内出框**；遮挡 **0.6 秒不消失** | 明亮场景、目标距镜头 ≥50 cm | 逐帧数描边像素 |
| 目标检测 | 空场景**零框**；目标出现**即出框**且框贴住目标 | 同上 | 逐帧数框内像素、算包围盒 |
| 长跑稳定性 | 15 分钟内帧均值漂移 **<1%** | 不断电、不动开关 | 取首尾两张对比 |
| 时序 | `Setup WNS > 0` 且 `TNS = 0` 且违例端点 = 0 | 最终版比特流 | 看 `route.qor` |

> **`[实践]` 反例（最痛的教训）**：我们换了两套伽马曲线、重新综合、重新烧板，屏幕上看不出区别，来回折腾两周。
> **根因不是曲线错，是没有判据**——"看起来好多了"不能作为判断依据。
> 后来学会用「逐列 R/G 极差」和「帧均值落点」，同一个问题十分钟就能判。

### 3.3 判据要能在**两张图**上自动算

好的判据有一个特征：**输入是两张图（或两段视频），输出是一个数**。

- 这样你可以写脚本批量算
- 这样你可以留证据（脚本 + 数据入库）
- 这样别人也能复现你的结论

**`[实践]`** 我们把「统计脚本 + 采集图 + 结论」三件套一起归档，报告里每个数字都能追到原始文件。

## 4. 单变量对照调试

### 4.1 一次只改一个变量

调试期最容易犯的错：同时改了三个东西，结果变好了，但**不知道是哪个起了作用**。

- 改参数 → 单独测
- 改 RTL → 单独测
- 改环境（光照/机位）→ 单独测

### 4.2 对照实验的标准做法

| 要素 | 要求 |
|---|---|
| **机位** | 全程不动（最好用支架，不要手持） |
| **光照** | 全程不动（同一个灯、同一个开关状态） |
| **被测对象** | 位置不动 |
| **唯一变量** | 只拨**一个**开关 / 只烧**一个**新版本 |
| **时间** | 两张间隔越短越好（≤5 秒） |

**`[实践]` 例子（判"暗角是镜头造成的还是场景造成的"）**：
白纸铺满画面 → 在纸上放一个标记物 → 拍一张 → **把相机原地转 180°** → 再拍一张。
- 如果暗角跟着标记物走 ⇒ 是**场景**问题
- 如果暗角固定在画面坐标不动 ⇒ 是**镜头/传感器**问题

这个实验一次就把"白平衡没调好"这个错误假设排掉了。

### 4.3 时间锚：证明两张图是同一时刻

两张图的差别，可能来自你要测的东西，也可能来自"场景自己变了"。怎么排除？

**`[实践]`** 我们在画面上叠了一个**帧计数器**。两张图的计数器差 = 帧数差，除以帧率 = 时间差。如果时间差和你的操作对得上，说明是同一段连续采集；对不上，说明中间断过电/重启过，两张图**不可比**。

**通用做法**：找设备上任何单调递增的量当时间锚（帧计数、时间戳、序号），叠在画面上或读进日志。

### 4.4 对照组：没有 A 就没有 B

任何"改进了"的结论，都必须有**同条件下的未改进版本**做对照。

**`[实践]`** 我们验"暗角校正有没有用"，最终靠的是「同一机位、同一光照、只拨一个开关」的两批独立采集，各给出一个极差数字，两次一致才算定案。

## 5. 假成功识别（四条判据）

**这是工程里最危险的一类错误：工具说成功了，板子也亮了，但你的代码根本没进去。**

### 5.1 四条判据（每次构建后都要过）

| # | 判据 | 怎么看 | 不通过说明什么 |
|---|---|---|---|
| 1 | **日志里没有黑盒警告** | 搜 `black box` / 关键字 `HDL-8007` 之类 | 新加的模块没进编译列表 |
| 2 | **新模块在网表里能搜到** | 在面积报告里搜模块实例名，看 LUT 数是否合理 | 模块被优化掉了 |
| 3 | **时序与资源数字发生了变化** | 对比 `route.qor` 的 WNS / slices / RAMs | 根本没重新综合 |
| 4 | **关键资源数没异常下降** | 比如 RAMs 从 40 掉到 12 | 整条链路被当冗余扫掉了 |

> **判据 3 是最灵敏的**：加了新逻辑，资源数**一个字节都没变**，那一定是没重新跑。

### 5.2 三个真实案例 `[实践]`

**案例 A：`.bit` 时间戳更新了，但网表没变**
- 现象：构建脚本报 exit=0，`.bit` 文件时间是新的
- 排查：`route.qor` 的数字和上一次**逐位相同**
- 根因：命令行流程读的是 **run 目录下的工程文件**，不是图形界面那份；只改后者不生效
- 教训：**时间戳新 ≠ 构建成功**

**案例 B：新模块是"黑盒"**
- 现象：报告里没有新模块，日志里有一行 `... is a black box in <顶层文件>(行号)`
- 根因：新文件没加进编译列表（而且工具还会**回写**列表文件，把你手工加的冲掉）
- 教训：**加新文件必须改"工具真正读的那份清单"**，并写脚本自动同步

**案例 C：整条链路被当冗余扫掉**
- 现象：上板黑屏，只剩 OSD；所有报告都是绿的
- 排查：`#RAMs` 从 40 掉到 12、`#DSPs` 从 9 掉到 1
- 根因：顶层某个输出端口忘了接，工具认为"这条链没人用"，把整条链优化掉了
- 教训：**资源数异常下降 = 有东西被删了**，要立刻查

### 5.3 固化的做法

把四条判据写进构建脚本，每次构建**自动检查并报红/报绿**。不要靠人眼看日志。

## 6. 工具链踩坑（按"类"记，不按工具记）

### 6.1 命令行与图形界面的工程文件不是同一份

**`[实践]` 坑**：图形界面维护的是 `.al`（工程描述），命令行流程读的是 run 目录下的 `.prj`（文件清单）。**只改前者，命令行看不到。**

**通用教训**：任何"两套配置"的工具有这个问题。加文件前先确认：**构建时到底读哪一份？**

### 6.2 工具会回写你手改的文件

**`[实践]` 坑**：跑完一次构建，工具会把 `.al` 重写一遍，把你手工加的行冲掉。下次构建就少了文件。

**通用教训**：手工改生成物之前，先确认它会不会被覆盖；会的话，**写成脚本每次构建前重新生成**。

### 6.3 相对路径静默失败

**`[实践]` 坑**：初始化文件用相对路径读表，工具的工作目录是 run 子目录，路径解析失败但它**不报错**，读成全 0。结果：表全零，上板全黑，但所有报告都是绿的。

**通用教训**：
- 关键数据表**优先内联到 RTL 里**，不要依赖外部文件路径
- 必须用外部文件时，**在构建后再检查一遍内容**
- 任何"静默失败"都要加断言

### 6.4 编码问题

**`[实践]` 坑**：源码带 BOM（`EF BB BF`）会让仿真器直接语法报错；中文注释被当非打印字符。

**通用教训**：
- 源码统一 **UTF-8 无 BOM**
- 改过编码的文件，**检查前 3 个字节**
- 命令行脚本**只写 ASCII**（中文可能被误码解码，一个汉字变问号吃掉引号，整脚本解析失败）

### 6.5 退出码不可信

**`[实践]` 坑**：命令行工具在"一行脚本都没跑"的情况下也可能返回 **exit code 0**。

**通用教训**：不要只看退出码，要看**产物是不是真的更新了**（时间戳 + 内容变化 + 日志关键字）。

### 6.6 别用 `Start-Process` 起长时间构建

**`[实践]` 坑**：用某种方式启动的工具会卡在中间阶段不动，进程活着但几十分钟无输出。

**通用教训**：长任务用**后台任务 + 轮询日志**，并设超时；卡住就杀掉重来，别等。

## 7. 上板验证

### 7.1 冷启动，不是按复位

**`[实践]`** 传感器/外设的初始化表通常只在**冷启动**时重来一次。按复位键不等于冷启动。

- 换版本后：**拔电 5 秒再上电**
- 改拨码后：如果改的是"开机才读"的参数，也要断电重启

### 7.2 把内部状态画到屏幕上（最实用的调试手段）

**`[实践]`** 我们在 OSD 里加了一行遥测：增益索引、状态机状态、帧均值、两个通道增益。
好处：
- 不用接逻辑分析仪，屏幕上直接读
- 截图就是证据，能进报告
- 现场演示时也是加分项（"画面实时显示参数变化"）

**代价**：占一点资源，交版前可以关掉或减层。

### 7.3 长跑

**`[实践]` 判据**：15 分钟不断电、不动开关，首尾帧均值漂移 <1%。

**意义**：短时间测不出来的漂移、死锁、寄存器被改写，只有长跑能暴露。

### 7.4 余量检查

时序余量很小时（比如只有几十 ps），改一点逻辑就可能翻负。
- 每次加逻辑后**先看 WNS**
- 留 ≥100 ps 的余量再冻结

## 8. 本节速查卡

```
改之前：先写判据（数值 + 条件 + 复查方式）
改之后：
  ├─ 构建：四条判据（黑盒 / 网表 / 数字变化 / 资源异常）
  ├─ 上板：冷启动 + 时间锚 + 对照组
  └─ 结论：脚本能算出数 + 两批一致
冻结后：只改常量，不改结构
```
