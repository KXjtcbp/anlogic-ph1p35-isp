# 05 · 常见问题与避坑清单

> 按阶段分类。带 `[实践]` 的是我们真踩过的，带 `[外部]` 的是同类竞赛常见说法。

---

## 1. 选题阶段

| # | 坑 | 表现 | 怎么避 |
|---|---|---|---|
| 1.1 | **把赛题的功能清单当成全部** | 做了一堆技术，说不清用途 | 在赛题原文里搜"应用""场景""实际意义"这些词，它们才是方向（见 `02` §3） |
| 1.2 | **写了应用场景但不落地** | 报告里有 5 个应用场景，删掉作品不受影响 | 自检：**把"应用"那段删掉，作品变不成立吗？** 不成立才算数 |
| 1.3 `[实践]` | **功能贪多** | 8 个功能，每个都半成品 | 只留 2~3 个，做到"能拍成视频" |
| 1.4 | **没有"30 秒瞬间"** | 演示讲五分钟评委还在问"所以它干什么" | 先设计那个瞬间，再倒推要做什么 |
| 1.5 | **选题时不看评分表** | 做了评分表上没写的功能 | 把评分表抄下来，逐条对应 |

## 2. 方案阶段

| # | 坑 | 表现 | 怎么避 |
|---|---|---|---|
| 2.1 | **先写代码后算资源** | 写到一半发现资源不够，推翻重来 | 先建资源预算表，留 20% 余量 |
| 2.2 `[实践]` | **资源全花在"看不见"的优化上** | 资源用了 80%，功能一眼看不出 | 明确留 20% 给"评委看得见的东西" |
| 2.3 | **架构选型没有理由** | 别人问"为什么这么分模块"答不出 | 每个架构决定写一行理由（帧式 vs 全流水、缓存 vs 直通） |
| 2.4 `[实践]` | **全部自研，不用任何现成轮子** | 技术扎实但功能数量少 | 核心链路自研 + 应用层用现成（见 `02` §5） |
| 2.5 | **没写退路** | 最难的模块做不出来就全崩 | 列出 3 个最可能失败的点，每个一条退路 |

## 3. 实现阶段

| # | 坑 | 表现 | 怎么避 |
|---|---|---|---|
| 3.1 `[实践]` | **常数乘法被推断成硬件乘法器** | 资源突然用满，时序翻负 | 常数乘法写成**移位加法**，并检查资源报告里乘法器数量 |
| 3.2 `[实践]` | **`wire` 漏写位宽** | 被推断成 1 bit，算术结果截断成最低位 | 任何做算术的 `wire` 都显式写位宽，**溢出判断要在截断之前做** |
| 3.3 `[实践]` | **同一 always 块里对同一寄存器多次非阻塞赋值** | 只有最后一条生效 | 拆成多个块，或改成清晰的分支 |
| 3.4 `[实践]` | **组合逻辑"回退"** | 状态机永远不动 | 组合输出的默认值不要覆盖掉刚算出来的结果（用中间寄存器暂存） |
| 3.5 `[实践]` | **把"帧末"信号当"行末"用** | 坐标计数器永远只加一次 | 确认每个同步信号的真实语义（`tlast` 是帧末还是行末？`tuser` 是帧首还是行首？） |
| 3.6 | **Testbench 只写"输入什么输出什么"** | TB 全过但上板错 | TB 要覆盖：边界值、旁路、热切换、**位宽/量纲**（见 3.7） |
| 3.7 `[实践]` | **两个模块各自的 TB 都过，接口却错了** | 量纲差 256 倍，靠人看才发现 | 两个模块的 TB 里，**激励要按对方的真实口径生成**，不要各按自己的理想口径 |
| 3.8 | **不加断言** | 数据异常时静默通过 | 关键路径加 `assert` 或仿真时主动检查 |

## 4. 调试阶段

| # | 坑 | 表现 | 怎么避 |
|---|---|---|---|
| 4.1 `[实践]` | **没有判据，靠肉眼** | "看起来好多了"→ 反复返工 | 动手前先写判据（见 `03` §3） |
| 4.2 `[实践]` | **同时改多个变量** | 变好了但不知道是哪个起作用 | 一次一个变量 |
| 4.3 `[实践]` | **没有对照组** | 结论站不住 | 同条件的未修改版本必须也在手边 |
| 4.4 `[实践]` | **两张图不是同一时刻** | 把场景变化当成改进效果 | 用帧计数/时间戳当时间锚 |
| 4.5 `[实践]` | **靶面不标准** | 用真实场景当"白纸"测白平衡 | 中性靶面（白纸/灰卡）铺满画面，且**贴平、挡光** |
| 4.6 | **只测一次就下结论** | 换个场景又不对 | 至少两批独立采集给出一致的数 |
| 4.7 `[实践]` | **测量脚本自己有 bug** | 统计区域遮错了，结论完全反 | 遮罩区域要**用代码自动定位**，不要手写坐标；算完打印出来核对 |
| 4.8 `[实践]` | **字面量位宽写错** | 40 bit 写成 12 个十六进制位被静默截断 | 用拼接 `{10'h0A2, 10'h13F, ...}` 而不是长字面量 |

## 5. 构建与工具链

| # | 坑 | 表现 | 怎么避 |
|---|---|---|---|
| 5.1 `[实践]` | **时间戳变新 ≠ 构建成功** | `.bit` 是新的，但内容没变 | 看 `route.qor` 的数字有没有变化（见 `03` §5） |
| 5.2 `[实践]` | **命令行读的工程文件 ≠ GUI 读的那份** | 加了文件，命令行看不见 | 找到"构建时真正读的那份清单" |
| 5.3 `[实践]` | **工具会回写你手改的工程文件** | 下次构建少了文件 | 写脚本每次构建前重新生成清单 |
| 5.4 `[实践]` | **相对路径静默失败** | 初始化表读成全 0，上板黑屏但报告全绿 | 表内联进代码；必须外置时构建后检查内容 |
| 5.5 `[实践]` | **BOM 导致语法报错** | 仿真器报非打印字符 | 源码统一 UTF-8 无 BOM，改完查前 3 字节 |
| 5.6 `[实践]` | **命令行脚本含中文** | 整脚本解析失败 | 命令行脚本只写 ASCII |
| 5.7 `[实践]` | **退出码 0 但什么都没跑** | 以为成功，烧了旧版本 | 查产物时间戳 + 日志关键字 + 内容变化 |
| 5.8 `[实践]` | **用 `Start-Process` 起长构建会卡死** | 进程活着但几十分钟无输出 | 后台任务 + 轮询 + 超时 |
| 5.9 | **不看日志只看结果** | 漏掉 `black box` 警告 | 构建脚本里 grep 关键字并报红 |
| 5.10 `[实践]` | **多个同名文件** | 改的文件根本没参与编译 | 用"这个文件在构建清单里吗"来确认，不要看目录里有没有 |

## 6. 上板

| # | 坑 | 表现 | 怎么避 |
|---|---|---|---|
| 6.1 `[实践]` | **按复位键不等于冷启动** | 传感器初始化表没重来 | 换版本/改开机参数：拔电 5 秒 |
| 6.2 `[实践]` | **拨码极性记反** | 以为开了其实关着 | 用 LED 或遥测显示实际电平，不要靠记忆 |
| 6.3 `[实践]` | **所有 `.bit` 大小相同** | 以为版本对 | 比 **md5** |
| 6.4 | **时序余量太小** | 改一点就翻负 | 冻结前留 ≥100 ps |
| 6.5 | **不测长跑** | 现场演示几分钟后出问题 | 15 分钟长跑，首尾漂移 <1% |
| 6.6 `[实践]` | **没有"已知良好"的回滚版本** | 出问题不知道是板子坏了还是代码坏了 | 每次里程碑存一个可回滚版本 |

## 9. 第一次参赛的典型问题（重点）

> 这一节专门写给第一次打这类比赛的人。**这些问题和技术能力无关，和"经验"有关。**

### 9.1 不知道"好作品长什么样"`[实践]`

第一次参赛最大的劣势不是不会写代码，是**没有参照物**。

- 你不知道往届获奖作品做到什么程度
- 你不知道评委看多久、看什么
- 你甚至不知道"完成度"这个词具体指什么

**怎么补**：
1. 找 3~5 个往届获奖作品的 B 站/小红书复盘视频，**只看"他们做了什么功能"和"他们怎么演示"**
2. 找对应竞赛的官方评分表，逐条抄下来
3. 加官方答疑群，翻历史消息（**这是最快的信息来源**）

### 9.2 把"技术难度"当成"评分依据"`[实践]`

第一次参赛常见的心态：**"我做的技术越难，分越高"**。

实际上赛题的评分轴通常包含"完成度""创新性""难度""系统功能与指标""演示效果"——**难度只占其中一项**。一个技术上普通但完整闭环的作品，往往比一个技术很难但不成形的作品分高。

### 9.3 选题阶段投入不足 `[实践]`

见 `01` §2。第一次参赛最典型的时间曲线是：**选题两天，方案一周，剩下全在写代码**。

结果是"实现质量很高，方向偏了"。

### 9.4 不知道怎么判断"做完了"`[实践]`

没有判据意识。典型表现：
- "看起来好多了"
- "应该没问题吧"
- "上一次是好的"

**怎么补**：见 `03` §3，从下一个功能开始，动手前先写一行判据。

### 9.5 不知道材料要交多全 `[实践]`

第一次参赛的人往往以为"代码交了就行"。实际要交的是一整套：代码 + 工程文件 + 约束 + IP 描述 + **时序/面积报告** + 比特流 + 报告 + 视频 + 海报 + 关键词。

**怎么补**：见 `04` §1，把清单提前两周列出来。

### 9.6 一个人扛全部 `[实践]`

第一次参赛常见：一个人写代码、一个人调板子、一个人写报告，互相不知道对方在干什么。

**怎么补**：见 `01` §5，按"可独立验收的产物"分工，并约定集成人。

## 10. 速查：如果只记 10 条

1. **先写判据再动手**，别用"看起来好多了"
2. **一次只改一个变量**，并且要有对照组
3. **拿设备自带的计数器当时间锚**，证明两张图是同一时刻
4. **构建后查四条**：黑盒 / 网表 / 数字变化 / 资源异常
5. **`.bit` 比 md5，不比大小**
6. **换版本拔电 5 秒**，按复位不算冷启动
7. **每个可上板版本存一份**，并记回滚方法
8. **代码包要带时序/面积报告和比特流**，不只是 `.v`
9. **仓库要 public**，提交前用无痕窗口验一次
10. **提前 1 小时交**
