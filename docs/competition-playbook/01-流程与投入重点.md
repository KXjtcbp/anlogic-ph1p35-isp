# 01 · 竞赛通用流程与各环节投入重点

---

## 1. 五阶段骨架（对绝大多数工科竞赛成立 `[外部]`）

```
选题 → 方案 → 实现 → 调试 → 提交/答辩
```

电赛、集创赛、嵌入式竞赛、智能车、FPGA 类，流程都是这一套。**差别只在时间长度和评审形式**（电赛四天三夜现场做、集创赛几个月周期、智能车分赛区+国赛），骨架不变。

---

## 2. 核心原则：返工成本指数递增 `[实践]`

这是全文最重要的一张表。**每个阶段"改主意"的代价不是线性的，是指数的。**

| 阶段 | 这个阶段改主意的代价 | 建议投入 | 我们本次实际投入 |
|---|---|---|---|
| **选题** | 换个方向 = 从零开始 | **20%** | 约 10% |
| **方案** | 换架构 = 推翻设计 | **20%** | 约 10% |
| **实现** | 换模块 = 重写代码 | 30% | 约 60% |
| **调试** | 换接口 = 全链路重验 | 20% | 约 15% |
| **提交** | 改材料 = 交不了了 | 10% | 约 5% |

> **`[实践]`** 我们这次的失分点精确落在这张表的第二列：选题 + 方案花了不到两周（<20%），剩下三个月全在实现和调试。
> 结果是**实现质量很高，但方向偏了**——做出来的东西技术上不差，但"没闭环"。

**推论**：如果时间紧，**砍实现，不要砍选题和方案**。一个想清楚了但功能少一半的作品，比一个功能做满但没人看得懂用途的作品分高。

---

## 3. 各阶段该干什么（附检查表）

### 3.1 选题（20%）

**产出物**：一句话方向 + 一张"评分项 ↔ 我的功能"对照表。

- [ ] 用 `02-题目到方向.md` 的四问法走一遍
- [ ] 能过"三分钟测试"：一句话说清「帮**谁**解决**什么**问题」
- [ ] 把赛题评分表逐条抄下来，右边填"我打算用哪个功能拿这条分"
- [ ] 数一遍：赛题允许做的功能里，我能做几个？**做 5 个平庸的，不如做 2 个能一眼看懂的**
- [ ] 找一个"外行也能激动"的演示瞬间（评委看 30 秒就能懂）

**`[实践]` 反例**：我们的报告里写了五个应用场景（工业检测 / 无人系统 / 嵌入式终端 / 教学验证 / 竞赛延伸），但这五段删掉作品一点不受影响——**说明那是叙述，不是方向**。

### 3.2 方案（20%）

**产出物**：架构图 + 资源预算表 + 风险清单。

- [ ] 先算资源再定架构（`03` §2）：LUT / ERAM / DSP / 带宽，各留 20% 余量
- [ ] 明确选**帧式**还是**全流水**（这是最根本的架构分歧，见 `03` §2.3）
- [ ] 列出"必须自己写"和"可以用现成"的边界（`03` §2.4）
- [ ] 找出 3 个最可能做不出来的点，每个写一个退路
- [ ] 定好"最小可交付"版本——先保证能交，再加分

**`[实践]` 教训**：我们所有算法都从零推（二维表拟合、倒数查表），技术扎实但**可做功能数量有限**；同类作品中常见的做法是移植开源算法做自己的应用——这不违规，见 `02` §5。

### 3.3 实现（30%）

**产出物**：可综合的 RTL + Testbench + 构建脚本。

- [ ] 先搭"最小通路"跑通，再加功能（不要一次写五个模块）
- [ ] 每个模块配一个 TB，**TB 必须能抓到 bug**（见 `03` §4.4）
- [ ] 构建用脚本，不用 GUI（见 `03` §5.1）
- [ ] 每次构建后核对"四条判据"（见 `03` §5.2）

### 3.4 调试（20%）

**产出物**：采集数据 + 判据通过记录。

- [ ] **先定判据再动手**（`03` §3.1）——这是本节最值钱的一条
- [ ] 单变量对照（`03` §3.2）：同机位、同光照、只改一个东西
- [ ] 拿设备自带的计数器/时间戳当"时间锚"（`03` §3.3）
- [ ] 每次改动留一行记录：改了什么 / 预期变化 / 实测变化

**`[实践]` 反例**：我们换了两套伽马曲线重烧，屏幕上看不出区别——**因为当时没有判据**。后来学会用"逐列 R/G 极差"和"帧均值落在目标 ±5%"，立刻就能判断。

### 3.5 提交 / 答辩（10%）

**产出物**：`04-提交前核查与打包.md` 全部打勾。

- [ ] 严格按清单逐项打勾，**不要凭记忆**
- [ ] 代码包在干净目录里重新打，不要在原始工作区直接压
- [ ] 所有二进制文件比 md5，不比大小（同类文件的字节数往往完全相同）
- [ ] 提前一天交，不要卡最后一小时

## 4. 时间表模板

把下表按你的赛程长度缩放（示例按 3 个月 / 12 周）：

| 周 | 里程碑 | 检查点 |
|---|---|---|
| W1–W2 | 定方向 + 架构 + 资源预算 | 能过三分钟测试；评分项对照表填满 |
| W3 | 最小通路跑通 | 端到端能出图 |
| W4–W7 | 核心功能 | 每 2 周一次构建 + 上板 |
| W8–W9 | 加分功能 | 从 `02` §4 的清单里挑，只挑 2 个 |
| W10 | 冻结功能 | **此后不再加功能** |
| W11 | 联调 + 回归 | 全功能逐项复测 |
| W12 | 材料 + 打包 + 演练 | `04` 全部打勾 |

**`[实践]` 死线要自己定早**：我们定的 RTL 冻结日是赛前 10 天，实际执行下来刚好够用。

## 5. 团队分工的粒度 `[实践]`

三个人 + 一块板子的典型配置：

- **不能按"模块"分**（"你写 AWB，我写 LSC"），因为模块之间有接口耦合，而且**只有一块板子，调试是串行的**。
- **要按"可独立验收的产物"分**：分支 + TB 全过 + 改动说明 + 预期现象。谁交付，谁负责到"能上板"为止。
- 改公共文件（顶层、约束、`.al`/`.prj`）前先打招呼，并在提交信息首行写明改了哪个公共文件。

> **`[实践]`** 我们的做法：`feat/xxx` 分支 + 四件交付物（分支 / TB 日志 / 编译检查输出 / 改动说明）+ `TOUCHES: design_top_wrapper.v` 标记。集成由一个人统一做，避免两人同时改顶层。

---

## 6. 本节最容易犯的三个错

1. **把"想清楚"当成浪费时间**——前 20% 的时间花在选题和方案上，看起来像没进展，实际是唯一能撬动总分的杠杆。
2. **用"功能数量"衡量进度**——赛题要的不是数量，是"完成度 + 能一眼看懂"。五个半成品不如两个完整的。
3. **调试靠肉眼**——"看起来好多了"不是判据。见 `03` §3.1。
